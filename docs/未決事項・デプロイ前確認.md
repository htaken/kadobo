# 未決事項・デプロイ前確認

要件定義 v1.1 §7「要確認事項」と、実装上の暫定パラメータ（コードにハードコードされている値）を、
確認先・期限・区分ごとに整理したもの。**「契約前に確定すべき」項目は A社との契約前に必ず解消すること。**
「自動化フェーズ前」の項目は MVP（手動運用）の間は未確定でも運用に支障はないが、`/keihi` モーダルや MF
連携を実装する前に確定させる。

**解決済みの項目については、根拠となる一次資料の URL・原文・取得日を §6「調査ログ（出典一覧）」に集約している。**
「〜のはず」で進めず、再確認が必要になったらその URL を再取得すること。

### 免税継続に伴う監視項目

**2027 年の課税売上高が 1,000 万円を超えると、登録の有無に関係なく 2029 年から強制的に課税事業者**になる
（2029 年分の基準期間は 2027 年の暦年フル）。免税事業者の基準期間の課税売上高は**税抜処理をしない**ため、
消費税相当額込みの受領額で判定される。

**時間単価 1,800 円では、閾値に届くのに年 5,051 時間（月平均 420.9 時間）を要するため、A社との取引
だけで到達することはない**（`1,000 万円 ÷ 1.1 ÷ 1,800 円 = 5,050.5 時間`）。⚠️ ただし**判定は事業全体の
課税売上高の合計**なので、他の取引先・単価改定・スポット売上が加わった場合は合算で見る。年間累計を
追う仕組みは残すが、監視の優先度は下げてよい。

> 🆕 **2026-09-27 訂正: 判定経路は基準期間だけではない。**基準期間（前々年）とは別に、
> **特定期間（個人事業者はその年の前年 1/1〜6/30）の課税売上高が 1,000 万円を超える**と
> **翌年から**課税事業者になる。2027 年上半期が超えれば 2028 年から、という経路が存在する。
>
> ただし**特定期間の判定は、課税売上高に代えて「その期間に支払った給与等の金額」で行うことを選べる**。
> **従業員も専従者給与も無い本件は給与等支払額が 0 円**なので、給与基準を選べば
> **特定期間で課税事業者になることはない**。→ **専従者給与を出し始める場合のみ復活する**経路。
> 詳細は `契約前確認事項.md` §1.2。

> - **丸めルール・跨日の帰属は、実装値がそのまま合意内容になった。**改修も過去分の再集計も不要

> - 源泉徴収は **10.21% の一律適用**で 100 万円超の 20.42% に未対応（旧 G1）。

> - `recomputeMonthly` は集計範囲を `${month}-01`〜月末で決め打ちしており、**月末締めにしか対応していない**。

### 4.2 浮動小数点誤差による請求額の過少計算（2026-09-27 発見・**修正済み・デプロイ済み**）

**時間単価 1,800 円を入れて検算したことで顕在化した、稼働中コードの実在欠陥。**

旧実装は `amount = Math.floor(hours * unit_price)` と書いていたが、`hours` は小数第 2 位までの
値なので、浮動小数点では真値をわずかに下回ることがある。

```
1.13 * 1800 === 2033.9999999999998   →  Math.floor() で 2033 円（正しくは 2034 円）
```

端数処理が `四捨五入` なら吸収されるが、**契約で `切捨` に確定したため、そのまま 1 円の過少請求**に
なる。月 400 時間までを 1 分刻みで全走査したところ、**報酬額で 842 件・消費税相当額で 280 件**が
ずれていた（全 24,001 通り中、約 3.5%）。金額としては 1 円だが、**A社が契約書の式どおりに手計算した
額とシステムの額が一致しない**という点が問題。

| | 修正内容 |
|---|---|
| 方針 | 乗算を整数で済ませてから割る（商が整数になる場合は必ず正確に表現されるため誤差が消える） |
| 報酬額 | `(小数第 2 位までの時間数 × 100 の整数) × 単価 ÷ 100` |
| 消費税相当額・源泉徴収額 | 率を 1/10000 単位の整数にして `金額 × 率の整数 ÷ 10000` |
| 実装箇所 | `gas/src/core/aggregate.ts`（`aggregateMonth`）、`gas/src/app/monthly.ts`（エラー行用 `hours`） |
| テスト | `gas/test/aggregate.test.ts` に**月 400 時間までの全走査回帰テスト**を追加（源泉 10.21% 側も含む） |

✅ **2026-09-27 に GAS へデプロイ済み**（`clasp push` → `clasp create-deployment --deploymentId ...` で
既存の web app デプロイを `@8` → `@9` へ更新。`/exec` URL は不変）。

⚠️ このとき Runbook 02 §B の**転送停止フラグは切り替えられなかった**（§4.3）。転送を止めずに
デプロイしたが、失敗した打刻は D1 に pending として残り Cron が再送するため、データ欠落は生じない。

### 6.4 OAuth・レート制限（#4）

出典:
[トークンエンドポイント](https://developers.biz.moneyforward.com/docs/api/auth/create-token) /
[API 共通仕様](https://developers.biz.moneyforward.com/docs/common/api_common_specifications) /
上記 OpenAPI 仕様の `components.securitySchemes`

v3 は経費 API のようなサービス個別 OAuth ではなく、**MFC 統合認可サーバー**を使う:

```yaml
AccessToken:
  type: oauth2
  authorizationUrl: https://api.biz.moneyforward.com/authorize
  tokenUrl:         https://api.biz.moneyforward.com/token
  refreshUrl:       https://api.biz.moneyforward.com/token
  scopes:
    mfc/invoice/data.write: Grant read and write access to all your office's data
    mfc/invoice/data.read:  Grant read-only access to all your office's data
```

**トークン寿命の数値は公開されていない。** 公式指針の原文:

> 取得したトークンは有効期限まで再利用してください。トークンを使用したとき、有効期限が切れて 401 を返した時は、
> このエンドポイントでトークンを更新してください。それまではトークンを再発行する必要はないため、
> 過度なアクセスはお控えください。

→ **要件定義 §4.4.1 の「アクセストークン 1 時間／リフレッシュトークン 540 日」は根拠のない前提**だった。
寿命をハードコードした先読み更新は壊れるため、**401 駆動のリアクティブ更新**に設計を変更する（§4.4.1 を更新済み）。

**レート制限**（API 共通仕様の原文）:

> 同一ユーザーから一定頻度以上のアクセスを検知した場合、次のように HTTP 429 エラーが返されます。
> 429 / `RATE_LIMIT_EXCEEDED` / Rate limit exceeded.
> レート制限はエンドポイント毎に独立しています。許容されるアクセス数はエンドポイントや状況により変化します。

数値は非公開。トークンエンドポイントは 429 時に `Retry-After`（秒）ヘッダを返す。
→ **実装は `Retry-After` を尊重するリトライにすること。**

**クライアント認証方式**は連携用アプリの設定に依存する（`CLIENT_SECRET_BASIC` = Basic 認証 /
`CLIENT_SECRET_POST` = リクエストボディ）。アプリポータルのアプリ詳細画面で確認が必要。

### 6.7 参考: MF クラウド経費 API（請求書 API とは別物）

出典: [クラウド経費 API OpenAPI 仕様](https://expense.moneyforward.com/api/index.json)（Swagger 2.0）/
[moneyforward/expense-api-doc](https://github.com/moneyforward/expense-api-doc)

kadobo が使うのは請求書 API だが、**経費 API の仕様から本プロジェクトの設計判断を裏付ける事実が 3 件取れた**ため記録する。

1. **インボイス経過措置 70% の裏付け**。`ExTransaction.invoice_kind` の定義は
   `enum: [1, 2, 3, 5]` / `1:対象外, 2:適格, 3:80%控除, **5:70%控除**`。
   §5 の「2026-10-01 以降は 70%」を、国税庁パンフレット以外の**稼働中の本番 API 仕様**でも確認できた。
   `4` が欠番で `5` が 70% に割り当てられており、将来の 50%・30% 用に番号を空けている設計と読める
2. **証憑区分の裏付け**。`ExTransaction.receipt_type` は `enum: ["e_doc", "paper"]` /
   `領収書タイプ(paper: 紙, e_doc: 電子取引)`。要件定義 v1.1 §9 の決定「証憑区分（紙／電子取引）を必須化」および
   経費台帳の `証憑区分` 列は、**MF が採用しているのと同じ 2 値**であり独自判断ではない
3. **スキャナ保存を採用しない判断の裏付け**。`EDocMetaDatum`（電子帳簿保存法書類情報）の必須項目には
   `timestamp_serial`／`timestamp_at`／`timestamp_version`／`timestamp_station_name`／`timestamp_expires_at`
   （タイムスタンプ局情報一式）が含まれ、ほかに解像度・階調・ページサイズも持つ。これらはスキャナ保存制度の要件であり、
   **紙原本保管を選択している kadobo には不要**。方針転換するとタイムスタンプ局との契約まで必要になることが読み取れる

なお経費 API は OAuth がサービスごとに独立しており（README 原文: 「クラウド経費の画面で発行した Client ID と
Client Secret、またアクセストークンを債務支払の API 実行に用いること、またその逆での動作は保証しかねます」）、
アクセストークン有効期限は約 32 日（`expires_in: 2775961`）、認可コードは 10 分。
**請求書 API v3 は統合認可サーバー（§6.4）を使うため値も方式も異なる**ので、混同しないこと。

### 6.10 🆕 青色申告特別控除の再編と「優良な電子帳簿」（2026-09-27）

令和 8 年度税制改正。**本ドキュメントの「65 万円控除」の記述はすべて改正前の前提**だった。

| 控除額 | 要件 |
|---|---|
| **75 万円** | 複式簿記 ＋ **e-Tax による期限内申告** ＋（**優良な電子帳簿** または **デジタルシームレス保存**） |
| **65 万円** | 複式簿記 ＋ **e-Tax による期限内申告** |
| 10 万円 | 簡易簿記（前々年収入 1,000 万円以下）／**複式簿記でも紙で申告した場合** |
| 0 円 | 簡易簿記かつ前々年収入が 1,000 万円超 |

適用は**令和9年（2027）分以後の所得税**から（個人住民税は令和10年度分以後）。

- **本件は e-Tax で申告する方針が確定しているため、65 万円は無条件に確保できる。**
  → §1 未確定 ④ から「青色申告 65 万円控除の要件」を外した
- 残る論点は **65 万円 → 75 万円の上積みを取りに行くか**だけ（差は年 10 万円の所得控除）

**なぜ 2026-12-31 が期限か**: **優良な電子帳簿はその年の最初から要件を満たして運用している
必要があり、年の途中から遡れない。**届出書自体は「適用を受けようとする年分の法定申告期限まで」
でよいが、**帳簿の実体が 2027-01-01 から要件を満たしていなければ意味がない。**

**優良な電子帳簿の要件**（仕訳帳・総勘定元帳）: 訂正・削除・追加の履歴が残ること、帳簿間の
相互関連性を確認できること、取引年月日・勘定科目・金額での検索および日付・金額の範囲指定検索が
できること、システム関係書類等の備付けとダウンロードの求めへの対応。
→ **これは MF クラウド確定申告側の機能で満たす話**であり、kadobo（経費台帳・Drive）の設計とは別問題。
MF のプラン別機能表（2026-06-18 更新）に優良な電子帳簿の行は無く、ページ原文に
**「表に記載されていないクラウド確定申告の機能は、ご契約中のプランに関わらず利用可能」**と
あるため、**パーソナルミニでも使える見込み**（要確認 1 件）。

**デジタルシームレス保存**（令和7年度改正で電帳法に新設。国税庁資料の原文）:

> 国税庁長官が定める基準に適合するシステムとは、➊デジタル庁が管理する仕様に従って送受信された
> デジタルインボイス（「Invoice JP PINT」又は「JP Self-Billing」）又は、❷**預貯金口座における
> 決済データ**のいずれかの電子取引データについて、上記の新設された要件に従って保存できる機能を
> 有するシステムのことをいいます。

送受信・保存の要件は ①訂正削除履歴が残る／そもそも訂正削除できないシステムで行う、②電子取引データの
金額を訂正削除したうえで電子帳簿に記録できないこと、③電子取引データと電子帳簿との相互関連性を
確認できること。**あらかじめ届出書の提出が必要**。効果は 75 万円控除に加えて**重加算税の 10% 加重の
適用除外**（令和9年1月1日以後に法定申告期限が到来する国税から）。

# 未決事項・デプロイ前確認

要件定義 v1.1 §7「要確認事項」と、実装上の暫定パラメータ（コードにハードコードされている値）を、
確認先・期限・区分ごとに整理したもの。**「契約前に確定すべき」項目は A社との契約前に必ず解消すること。**
「自動化フェーズ前」の項目は MVP（手動運用）の間は未確定でも運用に支障はないが、`/keihi` モーダルや MF
連携を実装する前に確定させる。

**解決済みの項目については、根拠となる一次資料の URL・原文・取得日を §6「調査ログ（出典一覧）」に集約している。**
「〜のはず」で進めず、再確認が必要になったらその URL を再取得すること。

| パラメータ | 実装値 | 実装箇所 | 対応する §7 項目 | 備考 |
|---|---|---|---|---|
| 消費税相当額の税率 | `ASSUMED_CONSUMPTION_TAX_RATE = 0.1`（10%） | `gas/src/core/aggregate.ts` | #7（課税／免税、インボイス経過措置） | 単価マスタの `tax_category` が「不課税」の行では計算に使われない（0 円）。課税区分そのものの要否は #7 の確定待ち |

| 分 → 時間の丸め | `hours = Math.round((worked_minutes / 60) * 100) / 100`（小数第 2 位） | `gas/src/core/aggregate.ts` | #5（丸めルール） | 月次請求の `hours` 列にのみ適用 |

>
> - `tax_inclusive` と `tax_display` は**単価マスタに列はあるが計算に使われていない**。
>   税込単価で合意すると消費税が二重計上、区分記載しない運用に合意すると源泉の計算基礎が過少になる
> - 源泉徴収は **10.21% の一律適用**で、100 万円超の部分に適用される 20.42% の 2 段階に未対応
> - `recomputeMonthly` は集計範囲を `${month}-01`〜月末で決め打ちしており、**月末締めにしか対応していない**。
>   `selectUnitPrice` も**月初日時点**で有効な単価行を選ぶため、月途中の単価改定は無視される

### 4.1 プラットフォーム上限に起因する実装リスク（2026-08-31 発見・**修正済み**）

§3 の #12 を調査する過程で見つかった、**MVP 稼働中のコードに実在した欠陥**。上表と違い契約内容とは
無関係だったため、A社の回答を待たずに修正した。

| リスク | 内容 | 実装箇所 | 対応 |
|---|---|---|---|
| ⚠️ **Cron 再送がサブリクエスト上限で途中停止する** | Workers **Free プランの外部サブリクエスト上限は 1 起動あたり 50 件**。`runRetryCron` は最大 50 件の pending を直列に GAS へ POST するが、GAS の `/exec` は必ず `script.googleusercontent.com` へ 302 を返し、`sendToGas` は `redirect: "follow"` のため **1 件あたり 2 件**を消費する。最悪 100 件となり上限の 2 倍。さらに `notifyRejectedDm`／`notifyRetryMention`（Slack API）も同じ枠を消費する | `worker/src/cron.ts`（`RETRY_BATCH_LIMIT`）、`worker/src/gas.ts:75`（`redirect: "follow"`） | ✅ **`RETRY_BATCH_LIMIT` を 50 → 20 に変更**（2026-08-31）。20 件なら全件に通知が付いても 50 件に収まる。cron は 5 分ごとに再実行されるため取りこぼしにはならない。実装設計 §6.6・§9 #9 にも反映済み |

> **発生条件**（修正前）: GAS 停止中に pending が 25 件以上たまった場合。1 人・1 日数打刻の運用では
> 長期停止が前提となるため確率は低い。ただし**「GAS が止まったときの再送」こそがこの cron の存在理由**
> であり、まさに必要な場面で機能しなくなる構造だった。
>
> ⚠️ **この修正を本番に反映するには Worker の再デプロイが必要**（`shared` は無変更のため Worker 側のみ）。
>
> なお D1 へのアクセスは「内部サービス」枠（Free プラン 1,000 件/起動）で別勘定のため、
> `recordAttemptResult` 等はこの上限に影響しない。

## 5. 確認済み・誤りやすい点への注記

- **インボイス経過措置の税率**: 2026-10-01 以降は **70%**（2028-09-30 まで）。50% や 30% ではない
  （50% は 2028-10-01〜2030-09-30、30% は 2030-10-01〜2031-09-30）。要件定義 §6.2 の表・出典（国税庁）を参照。
  この時期区分を誤ると単価協議・請求額に直接影響するため、契約前確認（§1 の #7）の際に必ず要件定義の表と
  照合すること。**2026-08-30 に国税庁パンフレット「インボイス制度に関する令和8年度税制改正について」
  （令和8年4月）で検証済み**（`docs/契約前確認事項.md` §4.1）。
- **売手側の措置も令和8年度改正で変わっている**: 2 割特例は**令和8年分（2026）で終了**し、
  令和9年分・令和10年分は個人事業者限定の **3 割特例**に引き継がれる。要件定義 v1.1 §6.2 には
  当初この売手側の措置が記載されておらず、2026-08-30 に追記した（`docs/契約前確認事項.md` §4.2）。
- 上記以外の暫定的決定（GAS の処理済みキーを内部シートではなく生ログの `idempotency_key` 列で判定する、
  nonce を `CacheService` のみで管理する 等）は要件定義に対する**実装上の決定**であり、業務ロジックの
  数値には影響しないため、本表には含めていない。詳細は `docs/実装設計_MVP.md` §9「要件定義 v1.1 からの
  差分・補足」を参照。

### 6.1 MF クラウド請求書 API の利用条件（#1）

出典: [マネーフォワード クラウド請求書APIについて](https://biz.moneyforward.com/support/invoice/guide/api-guide/a03.html)

> クラウド請求書を利用開始している場合、クラウド請求書APIは追加料金なく利用可能です。
> ただし、ご契約中のプランに応じてご利用可能な機能に制限がございますのでご留意ください。

> クラウド請求書APIをご利用の場合でも、取引先の登録数や郵送の可否等は「マネーフォワード クラウド」の
> 有料プランにおける制限と同様です。

**API バージョン管理ポリシー**: セマンティックバージョニングを採用。後方互換性のない変更は登録メール
アドレス宛に事前連絡されうる。提供終了する API にはサポート終了日・提供終了日が設けられ、開発ドキュメント
上に「非推奨」ラベルが表示される。→ **実装時は「非推奨」ラベルのないエンドポイントのみ使うこと。**

### 6.2 未送付作成と PDF 添付（#2）

出典: [クラウド請求書 API v3 OpenAPI 仕様](https://invoice.moneyforward.com/docs/api/v3/reference/iv_web_api.yaml)
（OpenAPI 3.1.0 / `info.version: 3.6.0`。[ドキュメントページ](https://invoice.moneyforward.com/docs/api/v3/index.html)は
Stoplight Elements の SPA なので、上記 YAML を直接取得する）

- **未送付での作成は保証される**。`POST /invoice_template_billings`（インボイス制度に対応した形式の請求書の作成）の
  レスポンス例 `NewBillingWithDeductPrice` は `payment_status: "未設定"` / `email_status: "未送信"` /
  `posting_status: "未郵送"` を返す
- `email_status` の定義は `null:未送信 / sent:送付済み / already_read:受領済み / received:受信`
- **さらに強い保証として、API 全 23 パスにメール送付エンドポイントが存在しない**。存在するのは
  `POST /billings/{billing_id}/posting`（**物理郵送**の依頼）と `GET /sent_histories`（送付履歴の**読み取り**）のみ。
  要件定義 §4.4.2 の「送付操作は自動化しない」は、運用方針ではなく **API 仕様として担保される**
- ❌ **PDF 添付エンドポイントは存在しない**。`Billing.pdf_url`（例:
  `https://invoice.moneyforward.com/api/v3/billings/{id}.pdf`）は **MF が生成した請求書 PDF を取得する URL** であって、
  こちらからファイルを添付する口ではない。日別明細 PDF の添付は MF 画面から手動で行う
  （代替として `note` 最大 2000 字 / `memo` 最大 450 字にテキストで埋め込む案もある）

[API 共通仕様](https://developers.biz.moneyforward.com/docs/common/api_common_specifications) /
上記 OpenAPI 仕様の `components.securitySchemes`

v3 は経費 API のようなサービス個別 OAuth ではなく、**MFC 統合認可サーバー**を使う:

```yaml
AccessToken:
  type: oauth2
  authorizationUrl: https://api.biz.moneyforward.com/authorize
  tokenUrl:         https://api.biz.moneyforward.com/token
  refreshUrl:       https://api.biz.moneyforward.com/token
  scopes:
    mfc/invoice/data.write: Grant read and write access to all your office's data
    mfc/invoice/data.read:  Grant read-only access to all your office's data
```

**トークン寿命の数値は公開されていない。** 公式指針の原文:

> 取得したトークンは有効期限まで再利用してください。トークンを使用したとき、有効期限が切れて 401 を返した時は、
> このエンドポイントでトークンを更新してください。それまではトークンを再発行する必要はないため、
> 過度なアクセスはお控えください。

→ **要件定義 §4.4.1 の「アクセストークン 1 時間／リフレッシュトークン 540 日」は根拠のない前提**だった。
寿命をハードコードした先読み更新は壊れるため、**401 駆動のリアクティブ更新**に設計を変更する（§4.4.1 を更新済み）。

**レート制限**（API 共通仕様の原文）:

> 同一ユーザーから一定頻度以上のアクセスを検知した場合、次のように HTTP 429 エラーが返されます。
> 429 / `RATE_LIMIT_EXCEEDED` / Rate limit exceeded.
> レート制限はエンドポイント毎に独立しています。許容されるアクセス数はエンドポイントや状況により変化します。

数値は非公開。トークンエンドポイントは 429 時に `Retry-After`（秒）ヘッダを返す。
→ **実装は `Retry-After` を尊重するリトライにすること。**

**クライアント認証方式**は連携用アプリの設定に依存する（`CLIENT_SECRET_BASIC` = Basic 認証 /
`CLIENT_SECRET_POST` = リクエストボディ）。アプリポータルのアプリ詳細画面で確認が必要。

### 6.5 Slack 無料プランのアプリ数上限（#11）

出典: [Slack CLI errors リファレンス](https://docs.slack.dev/tools/slack-cli/reference/errors)
（`service_limits_exceeded`。Context7 の `/websites/slack_dev` 経由で取得）

> Free Slack teams are limited to a maximum of 10 apps. If this limit is reached, you must upgrade your
> Slack plan to continue **creating** additional applications.

→ **自作（内部）アプリも 10 枠を消費する**。上限に達すると新規アプリの作成自体がブロックされる。
kadobo が 1 枠を使う前提で運用する。

参考（kadobo には影響なし）: 2025-05-29 の非 Marketplace アプリ向けレート制限変更について、
**内部の自作アプリは適用除外**（`conversations.history`／`conversations.replies` で 50+ req/min、
`limit` パラメータ最大 1,000 を維持）。

### 6.7 参考: MF クラウド経費 API（請求書 API とは別物）

出典: [クラウド経費 API OpenAPI 仕様](https://expense.moneyforward.com/api/index.json)（Swagger 2.0）/
[moneyforward/expense-api-doc](https://github.com/moneyforward/expense-api-doc)

kadobo が使うのは請求書 API だが、**経費 API の仕様から本プロジェクトの設計判断を裏付ける事実が 3 件取れた**ため記録する。

1. **インボイス経過措置 70% の裏付け**。`ExTransaction.invoice_kind` の定義は
   `enum: [1, 2, 3, 5]` / `1:対象外, 2:適格, 3:80%控除, **5:70%控除**`。
   §5 の「2026-10-01 以降は 70%」を、国税庁パンフレット以外の**稼働中の本番 API 仕様**でも確認できた。
   `4` が欠番で `5` が 70% に割り当てられており、将来の 50%・30% 用に番号を空けている設計と読める
2. **証憑区分の裏付け**。`ExTransaction.receipt_type` は `enum: ["e_doc", "paper"]` /
   `領収書タイプ(paper: 紙, e_doc: 電子取引)`。要件定義 v1.1 §9 の決定「証憑区分（紙／電子取引）を必須化」および
   経費台帳の `証憑区分` 列は、**MF が採用しているのと同じ 2 値**であり独自判断ではない
3. **スキャナ保存を採用しない判断の裏付け**。`EDocMetaDatum`（電子帳簿保存法書類情報）の必須項目には
   `timestamp_serial`／`timestamp_at`／`timestamp_version`／`timestamp_station_name`／`timestamp_expires_at`
   （タイムスタンプ局情報一式）が含まれ、ほかに解像度・階調・ページサイズも持つ。これらはスキャナ保存制度の要件であり、
   **紙原本保管を選択している kadobo には不要**。方針転換するとタイムスタンプ局との契約まで必要になることが読み取れる

なお経費 API は OAuth がサービスごとに独立しており（README 原文: 「クラウド経費の画面で発行した Client ID と
Client Secret、またアクセストークンを債務支払の API 実行に用いること、またその逆での動作は保証しかねます」）、
アクセストークン有効期限は約 32 日（`expires_in: 2775961`）、認可コードは 10 分。
**請求書 API v3 は統合認可サーバー（§6.4）を使うため値も方式も異なる**ので、混同しないこと。

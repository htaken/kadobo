# 稼働記録・経費管理システム 要件定義 v1.1

作成日: 2026-08-27（v1.0 同日改訂）／ 対象: 個人事業主（開業日 2026-09-01 予定）の稼働記録・経費・請求業務
改訂理由: v1.0 に対する Claude／Codex の独立レビュー（`reviews/統合レビュー_v1.0.md`）と、それに対する決定事項を反映。変更点一覧は §10。

---

## 1. 目的・背景

- 時間単価ベースの業務委託（A社）における**請求根拠としての稼働記録**を、Slack 操作だけで正確に残す
- 経費のレシート・台帳管理を Slack で完結させ、電子帳簿保存法に**適合する範囲を明確にして**運用する（紙レシートは紙原本を保管、電子取引は元データを保存。§4.3・§6）
- 月次の請求書作成をマネーフォワード（MF）連携で半自動化する
- 本システムは**受託者自身の自己管理・請求根拠ツール**であり、委託元が指定・管理する勤怠システムではない。Slack ワークスペース・チャンネル・データはすべて受託者が所有し、A社には月次の確定レポートのみ共有する（§6）
- 運用者は受託者本人のみ。Slack は**本人所有ワークスペースの、本人だけが参加するプライベートチャンネル**で使う（→ 操作者の認証・権限制御は不要と決定）

## 2. スコープ

**対象:**
- 稼働時間の打刻・修正・集計・単価計算（複数セッション／跨日を含む）
- 打刻の到達保証（GAS 失敗時の自動再送。ユーザーの押し直しを不要にする）
- 経費入力・証憑ファイル保存（紙レシート画像／電子取引の元データ）・経費台帳
- MF クラウド請求書の未送付請求書の自動生成、月次締めの状態管理

**対象外（現時点）:**
- 複数クライアント同時対応の高度化
- 入金消込の自動化（MF 銀行連携の明細を**人手で**消込する）
- 確定申告書作成そのもの、A社側システムとの直接連携
- 紙レシートの「スキャナ保存」（電帳法上の任意制度）— 採用しない。紙原本を保管する

## 3. システム構成

```
Slack（本人所有 WS／プライベートチャンネル／ボタン・モーダル）
   │  Request URL（interactivity・slash commands）
   ▼
Cloudflare Worker
   ├─ Slack 署名検証（raw body・timestamp ±5分・定時間比較）
   ├─ D1 受付ジャーナルに INSERT（冪等キー・action_ts・status=pending）
   ├─ 即時 ACK（目標 <500ms）
   ├─ モーダルを開く（views.open は trigger_id 3秒制約のため Worker が実行）
   ├─ view_submission の同期バリデーション（必須・金額・ファイル数/サイズ/拡張子）
   └─ waitUntil():
        ├─ chat.update → カードに「⏳ 記録中…」を即表示
        └─ GAS へ POST（本文 HMAC 認証、タイムアウト 20s）→ 成功で status=done
   Cron Trigger（5〜10分毎）: pending を GAS へ再送、N回失敗で本人にメンション
   │
   ▼
Cloudflare D1 … 受付ジャーナル（保持 30 日。記録の「正」ではない）
   │
   ▼
GAS Web アプリ … ビジネスロジック本体（HMAC・timestamp・nonce 検証）
   ├─▶ Google スプレッドシート（生ログ／日次集計／単価マスタ／月次請求／経費台帳／内部）
   ├─▶ Google Drive（証憑ファイル: 紙レシート画像・電子取引元データ）
   ├─▶ Slack Web API（chat.postMessage / chat.update / views.update / DM 通知）
   └─▶ MF クラウド請求書 API（月次・未送付請求書の作成）
          └─（MF 標準連携）→ MF クラウド会計に売上仕訳
```

### 3.1 責務分担

| コンポーネント | 責務 | 持つ秘密情報 |
|---|---|---|
| Worker | 署名検証、ジャーナル書込、ACK、モーダル表示、同期バリデーション、⏳表示、GAS 転送、再送、失敗通知 | Slack signing secret、Slack bot token、GAS 共有シークレット |
| D1 | 受付ジャーナル（at-least-once 配送の担保） | — |
| GAS | 状態遷移の検証、生ログ追記、集計、カード確定表示、経費処理、月次処理、時間トリガー | Slack bot token、GAS 共有シークレット、MF OAuth トークン |
| Sheets／Drive | 記録の「正」（生ログ・台帳・証憑ファイル） | — |

採用理由: Workers は V8 isolate によりコールドスタートが実質ゼロで、Slack の 3 秒 ACK と `trigger_id` の 3 秒制約を確実に満たす。GAS は Sheets/Drive に認証レスで接続できるため本体処理を担当。Worker 側の D1 ジャーナルにより、GAS の一時障害や `waitUntil()` の 30 秒上限で打刻が静かに消えることを防ぐ。

### 3.2 Slack アプリ設定

- 配布しないシングルワークスペースアプリ。Interactivity と Slash Commands の Request URL を Worker に向ける
- スコープ: `commands`、`chat:write`、`files:read`、`im:write`（DM 通知用）
- Bot をプライベートチャンネル `#稼働記録` に招待する
- Slack は**記録の保管場所ではない**（無料プランは 90 日超のメッセージが非表示、1 年超は削除）。証憑ファイルの `url_private` 取得はモーダル送信直後の処理で必ず完了させる

## 4. 機能要件

### 4.1 稼働記録

#### 4.1.1 稼働カード

- `/kado` コマンド、または平日朝（07〜08 時台）の GAS 時間トリガーで `#稼働記録` に**当日の稼働カード**を `chat.postMessage` で投稿し、`channel_id`・`message_ts` を内部シートに保存する（以後の更新は `chat.update`。`response_url` は 30 分・5 回制限があるため短期の受付通知にのみ使う）
- 平日判定は Google の日本の祝日カレンダー（`ja.japanese#holiday@group.v.calendar.google.com`）を `CalendarApp` で参照して祝日を除外する。年末年始等の任意休業日は内部シートで指定
- カードは**永続状態（生ログ）から毎回再描画**する。表示内容: 現在状態、当日の各セッション時刻、当日累計時間、その状態で有効なボタンのみ、直近イベントの処理状態（⏳／⚠️／✅）
- `/kado` で当日カードを再表示、`/kado status` で今週・今月の累計を ephemeral 表示
- 前日が「稼働中／休憩中」のまま残っている場合、朝のカードに警告と修正ボタンを表示

#### 4.1.2 状態機械

| 現在状態 | 操作 | 記録イベント | 次状態 | 備考 |
|---|---|---|---|---|
| 未稼働 | 開始 | `START` | 稼働中 | |
| 稼働中 | 休憩 | `BREAK_START` | 休憩中 | |
| 休憩中 | 再開 | `BREAK_END` | 稼働中 | |
| 稼働中 | 終了 | `END` | 確定 | |
| 休憩中 | 終了 | `END` | 確定 | 稼働終了時刻＝直前の `BREAK_START` 時刻。休憩時間は稼働に含めない |
| 確定 | 再開 | `START` | 稼働中 | 同日 2 セッション目以降。日次集計はセッション合計 |
| 任意 | ✏️ 修正 | `CORRECTION` | 変化なし | モーダル経由。元イベントは変更せず訂正イベントを追記（§4.1.4） |

表示ボタン: 未稼働 `[開始]` ／ 稼働中 `[休憩] [終了] [✏️修正]` ／ 休憩中 `[再開] [終了] [✏️修正]` ／ 確定 `[再開] [✏️修正]`

- **遷移可否は GAS が永続状態に基づいて検証する**。表に無い遷移（古いカードからの二度押し等）は記録せず、ephemeral で「すでに稼働中です」等を返してカードを再描画する
- 未稼働日はカードのみ存在し、取消操作は不要

#### 4.1.3 時刻・日付・冪等性

- **打刻時刻（`occurred_at`）は Slack が押下瞬間に付与する `action_ts`** を採用する。再送・遅延処理でも打刻時刻はズレない
- `received_at`（Worker 受信）、`processed_at`（GAS 処理）を別に保持する。すべて UTC epoch で保存し、表示・集計用に `Asia/Tokyo` の日時と**業務日**列を持つ。GAS プロジェクトのタイムゾーンは `Asia/Tokyo` に固定
- **跨日**（0 時を跨ぐセッション）は開始日の業務日に帰属させる（暫定。A社と合意の上で確定 → §7）
- **冪等キー** = `user_id + message_ts + action_id + action_ts`（モーダルは `view_id + hash`）。Worker は D1 に UNIQUE で記録、GAS は内部シートの処理済みキーで重複排除する。`LockService` で追記処理を直列化する

#### 4.1.4 修正

- カードの「✏️ 修正」で当日（および前日）のイベント時刻を修正できる。Worker は即時にローディング状態のモーダルを開き、GAS が当日ログを取得して `views.update` で差し替える
- 修正は**生ログの既存行を変更せず、`CORRECTION` イベントを新規追記**する（対象イベント ID・変更前値・変更後値・理由・修正日時）。複数回の修正は最新の訂正が有効。日次集計は訂正適用後の値で計算する
- 請求根拠の証跡として、修正履歴は月次明細 PDF の付記欄に件数を記載する

#### 4.1.5 到達保証（押し直し不要）

```
ボタン押下
  ▼
Worker: 署名検証
  ├─ D1 に受付ジャーナル INSERT（冪等キー, action_ts, status=pending）
  ├─ 即 ACK
  └─ waitUntil:
       ├─ chat.update → カードに「⏳ 開始 09:02 記録中…」
       └─ GAS へ POST（タイムアウト 20s）
            ├─ 成功 → status=done。GAS が確定表示に更新
            └─ 失敗 → pending のまま。カードを「⚠️ 記録待ち（自動再試行中）」に

Worker Cron Trigger（5〜10 分毎）
  └─ pending を GAS へ再送（冪等キーで重複排除）
       ├─ 成功 → done
       └─ N 回（例: 6 回 ≒ 1 時間）連続失敗 → 本人へメンション通知（確認用リンク付き）

GAS 22 時台トリガー（§4.1.6）
  └─ 「稼働中／休憩中のまま」＋「pending 残り」を検知して通知（最終セーフティネット）
```

- GAS 側の打刻処理は「遷移検証 → 生ログ 1 行追記 → chat.update」に限定し、通常 1〜3 秒で完了させる
- Worker の `waitUntil()` はレスポンス後最大 30 秒で打ち切られるため、GAS 呼び出しのタイムアウトは 25 秒（GAS 側のロック待ち 10 秒＋処理時間の内訳）とし、超過は「失敗」として再送に回す
- D1 ジャーナルは 30 日で削除（Cron）。記録の「正」は引き続きスプレッドシート

#### 4.1.6 押し忘れ・異常検知

- GAS 時間トリガー（**22 時台**。GAS のトリガーは指定時刻から ±15 分程度ずれる）で、当日が「稼働中／休憩中」のままの場合、終了時刻入力ボタン付きでメンション通知する
- 同トリガーで D1 の pending 残り（Worker の状態確認エンドポイント経由）と、生ログのペアリング不能（`START` に対応する `END` がない等）を検知して通知する

#### 4.1.7 生ログ列定義

| 列 | 内容 |
|---|---|
| `event_id` | ULID |
| `idempotency_key` | §4.1.3 |
| `business_date` | 業務日（JST、跨日は開始日） |
| `event_type` | `START` / `BREAK_START` / `BREAK_END` / `END` / `CORRECTION` |
| `occurred_at` / `occurred_at_jst` | 打刻時刻（`action_ts`）／JST 表示 |
| `received_at` / `processed_at` | Worker 受信／GAS 処理時刻 |
| `source` | `button` / `modal` / `retry` / `auto` |
| `session_no` | 当日のセッション番号 |
| `memo` | 任意メモ |
| `correction_of` / `old_value` / `new_value` / `reason` | `CORRECTION` のみ |

### 4.2 集計・単価計算

#### 4.2.1 シート構成（業務 5 シート＋内部 1 シート）

| シート | 主キー | 更新主体 | 手編集 |
|---|---|---|---|
| 生ログ | `event_id` | GAS（追記のみ） | 禁止 |
| 日次集計 | `business_date` | GAS（再計算） | 禁止（結果は「要修正」フラグで示す） |
| 単価マスタ | `client + 適用開始日` | 人手 | 可 |
| 月次請求 | `client + 対象月` | GAS＋人手（締め操作） | 締め状態に従う |
| 経費台帳 | `証憑ID` | GAS（追記）＋人手（MF 仕訳 ID 記入） | 一部可 |
| 内部 | — | GAS | 禁止（カード `ts`、処理済みキー、締め状態、任意休業日、設定値） |

#### 4.2.2 日次集計

- 業務日ごとに、訂正適用後のイベントを `occurred_at` 順に並べ、`START`〜`END` をセッションとして対にし、`BREAK_START`〜`BREAK_END` を差し引いて実稼働時間を秒単位で算出する
- 対にできない（`END` のない `START`、`BREAK_END` のない `BREAK_START` 等）場合は**自動集計せず「要修正」**とし、月次締め前チェックで一覧化する
- 丸めルール（暫定案、**A社と書面合意の上で確定** → §7）: 各セッションの秒を合算 → 日合計を分未満切り捨て → 月合計（分）→ 時間換算（小数 2 桁）。丸めの単位（1 分／15 分）と適用レベル（セッション／日／月）で請求額が変わるため、契約書に明記し、テストケースとして固定する

#### 4.2.3 単価マスタ

- 列: `client`、単価、税区分（課税／不課税）、税込／税抜、消費税相当額の記載方法、端数処理、源泉徴収区分・率、**適用開始日・適用終了日**（期間の重複禁止）
- 改定は新行追加で履歴管理。集計は業務日時点で有効な行を参照する

#### 4.2.4 月次請求

- 月合計時間 × 単価 → 報酬額。**報酬額・消費税相当額・源泉徴収額・差引入金予定額を分離**して保持する
- 月次締めの状態機械: `OPEN → REVIEWING → LOCKED → MF_CREATED → APPROVED → SENT → PAID / VOID`
  - `client + 対象月` を一意キーとし、MF 請求書 ID を保存して重複作成を防ぐ
  - `LOCKED` 以降は当該月の `CORRECTION` を受け付けず、差異は翌月調整として別途記録する
- MF 請求書の明細と 1:1 対応（例: 「○月分業務委託料 ○○h × ¥X,XXX」）

### 4.3 経費

#### 4.3.1 入力（`/keihi` モーダル）

| 項目 | 必須 | 内容 |
|---|---|---|
| 証憑区分 | ✔ | **紙**（店舗で受領した紙レシート）／**電子取引**（メール添付 PDF・EC サイトのダウンロード・Web 明細等） |
| 日付 | ✔ | 取引年月日 |
| 金額 | ✔ | 税込円（整数） |
| カテゴリ | ✔ | 通信費・消耗品費・旅費交通費・新聞図書費・会議費・支払手数料・その他（選択式） |
| 取引先 | ✔ | |
| メモ | | |
| 証憑ファイル | ✔ | `file_input`、`max_files: 1`、許可拡張子 `jpg/jpeg/png/heic/pdf`、上限 10MB（Slack は 100MB まで受け付けるが GAS の UrlFetch は 50MB 上限のため業務上限を設ける） |
| 税区分／事業使用割合 | | 任意（将来の課税事業者化に備えた列。初期は空欄可） |

- 証憑区分の初期値はファイルの MIME から推定（PDF → 電子取引、画像 → 紙）してよいが、最終的には本人が選ぶ
- **電子取引は受領した元ファイルをそのままアップロードする**。印刷して撮影した画像や画面スクリーンショットは電子取引の保存として認められないため、Worker は「電子取引＋画像ファイル」の組合せに確認警告を表示する
- 必須項目・金額・ファイル数/サイズ/拡張子の検証は **Worker が `view_submission` の同期応答（`response_action: errors`）で行う**（非同期ではモーダルにエラーを返せない）。非同期処理の失敗は Bot の DM で通知し、再実行ボタンを付ける

#### 4.3.2 保存処理（GAS）

1. `url_private` から Bot トークン（`files:read`）でファイルを取得し、SHA-256・元 MIME・サイズを記録
2. 証憑 ID（`R-YYYYMMDD-NNN`）を発行
3. Drive に保存: `/経費証憑/{紙|電子取引}/YYYY/MM/YYYYMMDD_金額円_取引先_証憑ID.{元拡張子}`（取引先名はファイル名に使えない文字を置換）
4. 経費台帳に 1 行追記
5. 処理状態を `RECEIVED → FILE_SAVED → LEDGER_SAVED → COMPLETED / ERROR` で記録。Drive 保存と台帳追記は非トランザクションのため、週次でファイルと台帳行の孤児照合を行う

経費台帳の列: 証憑 ID、証憑区分、日付、金額、取引先、カテゴリ、メモ、Drive リンク、ファイルハッシュ、元 MIME・サイズ、入力日時、処理状態、MF 仕訳 ID（月次で人手記入）

#### 4.3.3 電帳法上の位置づけ

| 証憑区分 | 電帳法上の区分 | 保存義務 | 本システムでの扱い |
|---|---|---|---|
| 紙 | 紙の書類 | 紙原本を保管（電子化＝スキャナ保存は任意制度。**採用しない**） | 画像は業務上の補助。**紙原本は捨てない**。保存期間は 7 年を標準（§6） |
| 電子取引 | 電子取引 | **受領した電子データそのものを保存する義務**（印刷保存は不可） | 元ファイルを Drive に保存。真実性は「電子取引データの訂正及び削除の防止に関する事務処理規程」（国税庁ひな形）の備付け・運用で確保。可視性は台帳の日付・金額・取引先で検索 |

- 入力期限: 受領後速やかに（7 営業日を目安）
- 検索要件: 基準期間の売上高 5,000 万円以下（開業 1〜2 年目は該当）でダウンロードの求めに応じる場合は不要だが、台帳の日付・金額・取引先列は MF 仕訳との紐付けにも使うため維持する
- 法定帳簿の「正」は MF クラウド会計／確定申告とし、Sheets の経費台帳は補助簿。MF 仕訳の摘要に証憑 ID を記載して相互関連を確保する。月次合算仕訳の可否は税理士に確認（§7）
- **暫定運用（経費機能が揃うまで）**: 紙レシートは紙原本を保管、電子取引の元データは Drive の所定フォルダに手動保存し、台帳には手入力する

### 4.4 請求（MF 連携）

#### 4.4.1 認証

- MF API は OAuth2（認可コードフロー）。アクセストークン有効期限 1 時間、リフレッシュトークン 540 日で、更新時に新しいリフレッシュトークンへ交換される（要再確認 → §7）
- GAS 用 OAuth2 ライブラリを使い、トークン更新は `LockService` 下で原子的に Script Properties へ保存する。401／429／タイムアウトは再試行、リフレッシュ失効時は再認可を Slack DM で通知する

#### 4.4.2 月次フロー

1. 月初の GAS トリガーが前月の日次集計を検査（「要修正」が無いこと）し、月次請求シートを更新して Slack に「締め確認」カードを投稿（`REVIEWING`）
2. 本人が内容を確認して `[締める]` → `LOCKED`
3. GAS が MF クラウド請求書 API で**未送付状態**の請求書を作成 → `MF_CREATED`。MF 請求書 ID を保存し、再実行時は作成をスキップする（**送付操作は自動化しない**）
4. 日別明細（日次集計の PDF）を Drive に保存。API での添付可否は要確認（不可なら MF 画面で手動添付）
5. Slack に作成完了を通知。本人が MF 画面で内容確認・送付 → `SENT`
6. 請求書 → 会計の標準連携で売掛金仕訳を自動計上（有効化条件は要確認）。入金は MF 銀行連携の明細を人手で消込 → `PAID`

MVP 期間中（§8）は 3〜4 を手動転記で代替する。

## 5. 非機能要件

### 5.1 応答性

- Slack への ACK は Worker が目標 500ms 以内（3 秒制約）。`views.open` も Worker が 3 秒以内に実行
- GAS の打刻処理は目標 5 秒以内、Worker 側タイムアウト 25 秒（`waitUntil()` 30 秒上限の内側。内訳は GAS のロック待ち最大 10 秒＋処理時間）
- 経費・月次の GAS 処理は 30 秒以内を目標（上限は GAS の 6 分）

### 5.2 セキュリティ

- **Slack 署名検証（Worker）**: `X-Slack-Signature` を **raw body** で HMAC-SHA256 検証、`X-Slack-Request-Timestamp` が現在時刻 ±5 分以内であること、定時間比較。不正時は 401 を返しログに記録する。検証前に body を URL デコード・JSON 再シリアライズしない
- **Worker → GAS 認証（本文エンベロープ）**: GAS の `doPost(e)` は HTTP ヘッダーを読めないため、`{ ts, nonce, payload, sig }` を POST 本文に入れる。`sig = HMAC-SHA256(secret, ts + "." + nonce + "." + JSON(payload))`。GAS は `|now − ts| ≤ 300 秒`、nonce 未使用（`CacheService` 10 分＋内部シート）、署名一致（定時間比較）を検証する。固定シークレットのみではリプレイ可能なため不可
- GAS Web アプリは「実行ユーザー: 自分」「アクセス: 全員（匿名）」でデプロイする。URL は公開エンドポイントになることを前提に、上記の認証で守る。デプロイ更新手順・所有アカウント・障害時の停止手順（Worker 側でフラグ）を運用手順書に記載
- 秘密情報は Worker の Secrets／GAS の Script Properties に保存。コードに直書きしない。ログに bot token・`response_url`・署名を出力しない
- Drive の証憑フォルダは非公開（本人のみ）、編集者を増やさない、Google アカウントは 2 段階認証
- 操作者の認証・権限制御は行わない（本人のみのプライベートチャンネルで運用するため。§1）

### 5.3 到達保証・整合性

- 配送は at-least-once（D1 ジャーナル＋Cron 再送）、処理は冪等（冪等キー＋処理済みキー）
- カードは永続状態から再描画し、Sheets 更新成功後の Slack 更新失敗による表示乖離は次回操作・`/kado`・朝のカード投稿で解消する

### 5.4 コスト（想定。上限監視を行う）

- Cloudflare Workers Free（10 万 req/日）、D1 Free（書込 10 万行/日）、Cron Triggers（Free プランで利用可）
- GAS 無料（トリガー総実行時間・UrlFetch 回数の日次クォータ内）
- Google Drive 無料 15GB（証憑 1MB × 数百件/年で十分）
- Slack 無料プラン（Block Kit・モーダル可。アプリ数上限 10 に自作アプリが含まれるか要確認 → §7）
- MF はプランにより API 利用可否・料金が異なる（要確認 → §7）

### 5.5 可用性・保全

- 生ログは追記専用。修正は `CORRECTION` 追記で履歴を残す
- **バックアップ**: 月次の GAS トリガーでスプレッドシートを xlsx にエクスポートし、証憑フォルダと合わせて別の Drive フォルダ（バックアップ専用）に保存。Drive の版管理は独立したバックアップとみなさない
- 年 1 回、バックアップからの復元手順を実際に試す
- D1 ジャーナルの保持は 30 日

### 5.6 監視・通知

- GAS 例外・Worker の GAS 呼び出し失敗は Slack DM に通知（処理 ID 付き）
- Cron 再送が N 回連続失敗した場合は本人にメンション
- 週次で証憑ファイルと台帳行の孤児照合結果を通知

## 6. 法令・制度要件

### 6.1 電子帳簿保存法

- 紙で受領した領収書は紙原本を保管する（スキャナ保存は採用しない）
- 電子取引データは元データを Drive に保存し、事務処理規程（国税庁ひな形「電子取引データの訂正及び削除の防止に関する事務処理規程」）を備え付けて運用する。検索は台帳で担保する（§4.3.3）
- 保存期間は 7 年を標準とする（申告区分・所得により 5 年／7 年が異なるため税理士に確認 → §7）
- 法定帳簿の「正」は MF、Sheets は補助簿。証憑 ID で相互関連を確保する

### 6.2 インボイス制度

- 開業時は免税事業者を想定（要確認 → §7）。適格請求書は発行できないため、**適格請求書ではない請求書**（買手の経過措置適用に必要な、区分記載請求書と同等の記載事項を満たすもの）を発行する。登録番号欄は設けない
- 買手（A社）の仕入税額控除の経過措置は**令和8年度税制改正で見直され**、次のとおり:

  | 期間 | 控除割合 |
  |---|---|
  | 2023-10-01 〜 2026-09-30 | 80% |
  | **2026-10-01 〜 2028-09-30** | **70%** |
  | 2028-10-01 〜 2030-09-30 | 50% |
  | 2030-10-01 〜 2031-09-30 | 30% |
  | 2031-10-01 以降 | 控除不可 |

  出典: 国税庁「令和8年度税制改正における免税事業者からの課税仕入れに係る経過措置について」
  https://www.nta.go.jp/taxes/shiraberu/zeimokubetsu/shohi/keigenzeiritsu/invoice-review/

- **開業 1 か月後（2026-10-01）に 80%→70% の切替**が来るため、単価・消費税相当額の扱い・登録の要否は契約前に A社と協議する
- 消費税相当額を請求する場合、報酬額と消費税相当額を区分して記載する（源泉徴収の対象を報酬額のみにできる場合がある。国税庁タックスアンサー No.2792）

### 6.3 源泉徴収

- 個人への業務委託であっても源泉徴収の要否は**業務内容**（所得税法 204 条の列挙業務に該当するか）で決まる。A社および税理士に確認（§7）。単価マスタに源泉区分・率を持ち、請求書に源泉徴収額を表示できるようにする

### 6.4 フリーランス・事業者間取引適正化等法

- A社が従業員を使用する事業者であれば適用対象。取引条件（業務内容・報酬額・支払期日等）の書面またはメールでの明示義務、報酬の支払期日は原則として給付受領日から **60 日以内**。適用有無を確認し、契約書・発注書に業務内容・提供日・単価・締め日・支払日・検査・経費負担を明記する（§7）

### 6.5 偽装請負・労働者性

- 名称（「稼働記録」）・ツールの所有・運用主体だけでは回避できず、**実態**（諾否の自由、具体的な指揮監督の有無、時間・場所の拘束、代替性、報酬の労務対償性）で判断される
- 契約・運用で担保する事項: A社が日々の開始・終了を承認しない、休暇の許可を求めない、作業方法・時間・場所を原則自己決定する、稼働記録は受託者の自己記録であり A社へは月次の確定レポート（請求明細）のみ共有する。時間単価そのものは直ちに問題とならないが、実態評価は専門家に確認する

### 8.1 MVP 受入条件（抜粋）

- ボタン連打・古いカードからの操作で生ログに重複や不正遷移が記録されない
- GAS を意図的に停止した状態で打刻 → カードが「⚠️ 記録待ち」になり、GAS 復旧後に Cron 再送で `action_ts` の時刻どおり記録され、ユーザー操作なしで「✅」になる
- 休憩中に終了 → 稼働終了時刻が直前の休憩開始時刻になる
- 同日 2 セッション（終了 → 再開 → 終了）の日次集計がセッション合計になる
- 修正モーダルで時刻を変更 → 生ログの元行は不変、`CORRECTION` 行が追記され、日次集計は訂正後の値になる
- 不正な Slack 署名・古い timestamp・偽の GAS エンベロープがそれぞれ拒否される

## 9. 決定事項ログ

### v1.0（2026-08-27）
- 報酬体系: 時間単価ベース（時給 × 稼働時間）→ 稼働ログ＝請求根拠
- アーキテクチャ: **最初から Cloudflare Worker を前段に配置**（GAS 単体案は不採用）
- 請求書送付: 自動生成は未送付状態まで、送付判断は人間

### v1.1（2026-08-27）
- Slack は本人所有ワークスペースの本人のみプライベートチャンネルで運用 → 操作者の認証・権限制御は不要
- 打刻の到達保証: Worker の D1 ジャーナル＋Cron 再送で at-least-once。**ユーザーは押し直さない**。打刻時刻は `action_ts`
- 紙レシートは**スキャナ保存を選択せず紙原本を保管**。電子取引は元データ保存＋事務処理規程。経費入力に**証憑区分（紙／電子取引）を必須化**
- 「Slack モーダル＋Drive＋台帳を正とする」（v1.0）は撤回し、法定帳簿の正は MF、Sheets は補助簿。MF アプリでの二重撮影はしない方針は維持
- 修正は `CORRECTION` イベント追記方式（生ログは真に追記専用）
- モーダル表示（`views.open`）と同期バリデーションは Worker が担当
- カードは `chat.postMessage` で投稿し `chat.update` で更新。`response_url` は短期通知のみ
- Worker → GAS 認証は本文エンベロープ（HMAC＋timestamp＋nonce）
- 状態機械に `休憩中→終了`、`確定→再開`（複数セッション）を追加。跨日は開始日帰属（暫定）
- 月次締めに状態機械を導入し、`client + 対象月` で重複請求書を防止

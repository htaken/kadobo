## 0. 実装体制と原則

- MVP 設計 §0 と同じ。コードは Agent（sonnet）に委譲し、**本書が契約**。WP 単位でレビューする
- MVP と同じヘキサゴナル構成を維持する: `core`（純関数・GAS API 非依存）／`app`（ユースケース、`ports.ts` の型だけに依存）／`adapters`（GAS グローバル）
- **新しい外部 I/O は必ずポートを増やして注入する**。ユースケースから `DriveApp`・`UrlFetchApp` を直接触らない
- **外部副作用（Drive 保存）を伴う at-least-once 配送**であることを常に意識する。「重複しない」は事後検知ではなく**処理順で保証する**

## 1. スコープ

### 含む

| | 内容 |
|---|---|
| Slack | `/keihi` によるモーダル入力（証憑区分・日付・金額・カテゴリ・取引先・メモ・証憑ファイル） |
| Worker | モーダルの生成・`views.open`、`view_submission` の同期バリデーション、D1 ジャーナル、GAS 転送、Cron 再送 |
| GAS | Slack からのファイル取得、SHA-256、証憑 ID 発行、Drive 保存、経費台帳追記、処理状態管理 |
| GAS | 週次の突合（Drive と台帳の全件照合）、訂正・取消 |
| 運用 | Drive のフォルダ構成、事務処理規程の備付け、受入試験、ロールバック手順 |

### 含まない（別フェーズ）

- MF クラウド請求書 API 連携・月次締め状態機械（仕様調査は `docs/未決事項・デプロイ前確認.md` §6 に完了済み）
- MF クラウド会計への仕訳自動連携（`MF仕訳ID` 列は引き続き**月次で人手記入**）
- スキャナ保存制度への対応（要件定義 §9 v1.1 で**採用しないと決定済み**。§6 参照）

## 2. Slack 側の識別子（固定）

### 2.1 スラッシュコマンド

| コマンド | 引数 | 動作 |
|---|---|---|
| `/keihi` | なし | 経費入力モーダルを開く（引数が付いていても無視する） |

> MVP では `/keihi` は定型 ephemeral を返すだけだった（MVP 設計 §6.5-1）。本フェーズでその分岐を置き換える。

### 2.2 経費モーダル（`callback_id: kado_expense`）

`title: 経費の登録` / `submit: 登録` / `close: キャンセル`。**入力要素はすべて `input` ブロックに置く**
（`file_input` は `input` ブロック内に置く必要がある）。

| # | `block_id` | `action_id` | 要素 | 必須 | 備考 |
|---|---|---|---|---|---|
| 1 | `receipt_type` | `receipt_type_select` | `static_select` | ✔ | `paper`（紙）／`e_doc`（電子取引）。**初期選択は置かない**（§7 #E3） |
| 2 | `date` | `date_pick` | `datepicker` | ✔ | 取引年月日。`initial_date` は当日（JST） |
| 3 | `amount` | `amount_input` | `plain_text_input` | ✔ | 税込円（整数） |
| 4 | `category` | `category_select` | `static_select` | ✔ | §2.3 の 7 種 |
| 5 | `partner` | `partner_input` | `plain_text_input` | ✔ | 取引先。最大 100 字 |
| 6 | `memo` | `memo_input` | `plain_text_input`（`multiline`） | | 最大 200 字。`optional: true` |
| 7 | `file` | `file_upload` | `file_input` | ✔ | `filetypes: ["jpg","jpeg","png","heic","pdf"]`、**`max_files: 1`** |

🔄 **初版にあった `edoc_confirm`（電子取引＋画像のときの確認チェックボックス）は削除した。** 理由は §7 #E1。
代わりに `file` ブロックの `hint` に次の案内を出す（**検査ではなく案内**）:

> ダウンロードできる原本（PDF 等）があるときは原本を添付してください。Web やアプリでしか表示されない場合は、
> 日付・取引先・金額が判読できるスクリーンショットで構いません。

- 🔄 **`private_metadata` には `{"channel_id": "<コマンド実行チャンネル>"}` を入れる**（2026-08-31 の WP6 レビューで訂正。初版は「空文字列でよい」と書いていたが誤り）
  - `expense_submit` は `channel_id` を必須とする（§3.1）のに、**`view_submission` のペイロードには channel 情報が無い**（`block_actions` の `payload.channel.id` に相当するものが存在しない）。`/keihi` を受けた時点でしか実行チャンネルを知り得ないため、`views.open` の際に `private_metadata` へ載せて引き継ぐ
  - 既存の修正モーダルが `CorrectionPrivateMetadata`（`channel_id`/`message_ts`/`business_date`）で行っているのと同じ方式。`view_submission` 側は壊れていた場合に備えて防御的にパースする
- `file_input` は **`files:read` スコープが必須**、Slack 側の上限は 100MB
  （<https://docs.slack.dev/reference/block-kit/block-elements/file-input-element>）。業務上限 10MB は §4.3 で別途検証する

### 2.3 共有定数（`shared/src/expense.ts`）

Worker（モーダル生成・検証）と GAS（検証）が同じ定義を読む。**`shared/package.json` の `exports` にも追加する**
（`@kadobo/shared/expense` として解決できるようにする。初版はこれを書き落としていた）。

```ts
export const EXPENSE_CATEGORIES = [
  "通信費", "消耗品費", "旅費交通費", "新聞図書費", "会議費", "支払手数料", "その他",
] as const;
export type ExpenseCategory = (typeof EXPENSE_CATEGORIES)[number];

export const RECEIPT_TYPES = ["paper", "e_doc"] as const;   // 紙 / 電子取引
export type ReceiptType = (typeof RECEIPT_TYPES)[number];

export const EXPENSE_ALLOWED_EXTENSIONS = ["jpg", "jpeg", "png", "heic", "pdf"] as const;
export const EXPENSE_MAX_FILE_BYTES = 10 * 1024 * 1024;      // 業務上限 10MB

/** `url_private` の取得を許可するホスト（§5.5 の SSRF 対策）。 */
export const SLACK_FILE_ALLOWED_HOSTS = ["files.slack.com", "slack.com"] as const;
```

> `receipt_type` の値を **MF クラウド経費 API の `receipt_type`（`paper`/`e_doc`）と同じ語**にしてある
> （`docs/未決事項・デプロイ前確認.md` §6.7-2）。

### 2.4 Slack アプリ manifest の差分

- スコープ: `files:read` は初回デプロイ時の manifest に含まれている。**インストール済みアプリに実際に付与されているかは §8 の S1 で確認する**
- Slash command `/keihi`・Request URL は変更不要

## 3. Worker ↔ GAS プロトコル拡張

### 3.1 新しいペイロード種別（MVP 設計 §3.2 に追加）

```ts
| { kind: 'expense_submit'; idempotency_key: string; user_id: string; view_id: string;
    channel_id: string;      // 🔄 通知先。cron.ts が全 pending で参照するため必須（§4.5）
    receipt_type: 'paper'|'e_doc';
    date: string;            // YYYY-MM-DD（取引年月日）
    amount: number;          // 税込円、正の整数
    category: ExpenseCategory;
    partner: string;
    memo: string;            // 未入力は ''
    file: {
      id: string;            // Slack file id（F...）
      name: string;
      mimetype: string;
      filetype: string;
      size: number;          // bytes（Slack の申告値。GAS は実サイズも検証する）
      url_private: string;
    };
    received_at_ms: number; source: 'modal'|'retry' }
```

- **封筒（§3.1）・署名・nonce は MVP と完全に同一**。変更しない
- `source` に `'retry'` を含める＝ **Cron 再送の対象**。`open_correction` と違いモーダルは閉じており陳腐化しない
- `file.url_private` の取得には `Authorization: Bearer <bot token>` が必要
  （<https://docs.slack.dev/reference/objects/file-object>）。**トークンは payload に載せない**。GAS が Script Property を使う
- 🔄 **`channel_id` を追加した理由**: `worker/src/cron.ts:73` は再送失敗の通知で `original.channel_id` を参照する。
  これを欠くと `expense_submit` が `GasRequest` union に入った時点で**型が通らない**（初版の見落とし）

### 3.2 レスポンス（MVP 設計 §3.3 に追加するエラーコード）

`GasResponse` の形は変えない。🔄 HTTP ステータスごとに分類を明確化した（初版は「4xx を一括で再試行」に読めた）。

| `error` | `retryable` | 発生源 | Worker の動作 |
|---|---|---|---|
| `FILE_NOT_FOUND` | `false` | `url_private` が **404**（ユーザーがファイルを削除した） | `rejected` → DM |
| `FILE_FORBIDDEN` | `false` | **401/403**（スコープ未付与・トークン失効・権限取消） | `rejected` → DM（**設定エラーなので運用者への警告文言にする**） |
| `FILE_TOO_LARGE` | `false` | 実ダウンロードサイズが業務上限超過 | `rejected` → DM |
| `FILE_INVALID` | `false` | Content-Type・マジックバイトが許可形式と一致しない | `rejected` → DM |
| `FILE_FETCH_FAILED` | `true` | **429（`Retry-After` に従う）／5xx／3xx／通信失敗** | `pending` → Cron 再送 |
| `FILE_UNAVAILABLE` | `false` | 🔄 **上記以外の 4xx**（400・410 等）。2026-09-01 の WP8a レビューで追加 | `rejected` → DM |
| `DRIVE_FAILED` | `true` | Drive の一時失敗 | `pending` → Cron 再送 |
| `DRIVE_CONFLICT` | `false` | 同名ファイルが 2 件以上／サイズ不一致（§5.4 フェーズ 3） | `rejected` → DM（**手動確認が要る**） |
| `DUPLICATE`（`ok:true, applied:false` の `reason`） | — | 同一冪等キーの台帳行が `COMPLETED` | `done` |

`FILE_*` 系は **`GAS_PRE_APPLY_ERRORS` に加えない**（台帳行を作った後に判明しうるため、
「未適用と確定できる」条件（MVP 設計 §3.3）を満たさない）。

> 🔄 **未分類コードを retryable に倒してはならない**（2026-09-01 追記）。Cron 再送は**回数上限を持たない**
> （`RETRY_NOTIFY_AT` 到達後は `RETRY_NOTIFY_EVERY` ごとに通知するだけで諦めない）ため、恒久的な 4xx を
> retryable にすると**無限に再送し 6 時間ごとにメンションが飛び続け、行が永久に `pending` のまま残る**。
> HTTP のセマンティクス（4xx＝クライアント誤りで自然には直らない／5xx＝サーバ側で直りうる）に従い、
> **未分類の 4xx は非再試行、それ以外の未分類コードは再試行**とする。非再試行なら DM が飛び、
> 利用者は `/keihi` からやり直せる。

## 4. Worker の処理フロー

### 4.1 `/keihi`（MVP 設計 §6.5-1 を置き換え）

```
1. §2.2 のモーダル JSON を組み立てる（静的。データ参照は不要）
2. ctx.waitUntil(views.open(trigger_id, view)) を開始する
3. 直ちに 200 空ボディを返す
```

- 🔄 **`views.open` の完了を待たずに ACK する**。`trigger_id` は 3 秒で失効するため、待って ACK すると
  Slack の 3 秒制約と競合する。応答を待たずに開始し、失敗時のみ `response_url` へ ephemeral でエラーを返す
- **GAS へは転送しない。D1 ジャーナルにも書かない**（モーダルを開くだけでは業務状態が変わらない）
- 修正モーダル（`open_correction`）と違い**ローディングビューを挟まない**（表示が静的で GAS 往復が不要）

### 4.2 `view_submission`（`callback_id: kado_expense`）

```
1. state.values を §4.3 に従って検証 → NG なら {response_action:'errors', errors:{...}} を同期で返す
2. 冪等キー生成 → D1 INSERT
     ├─ 成功／重複 → {response_action:'clear'} を返す
     └─ 🔄 INSERT 自体が失敗 → clear せず {response_action:'errors'} で
        「受け付けに失敗しました。もう一度お試しください」を返す（握り潰すと入力内容が失われる）
3. waitUntil: GAS へ POST（§3）。失敗は pending のまま Cron 再送
```

`index.ts` のルーティングは `payload.view.callback_id` で `kado_correction` / `kado_expense` を分岐する。

### 4.3 同期バリデーション仕様

| 対象 `block_id` | 検証 | エラーメッセージ |
|---|---|---|
| `receipt_type` | 未選択でない。値が `paper` / `e_doc` のいずれか | 証憑区分を選択してください |
| `date` | 未選択でない | 日付を選択してください |
| `date` | 🔄 **`YYYY-MM-DD` 形式かつ実在する日付**（`shared/src/time.ts` の `isValidDateString`。うるう年考慮、`Date` のパースに頼らない） | 日付を選択してください（形式専用の新しい文言は作らない） |
| `date` | **未来日でない**（JST の当日まで） | 未来の日付は登録できません |
| `amount` | カンマ・空白除去後に `/^[0-9]+$/`、**1 以上の整数** | 金額を半角数字で入力してください |
| `category` | `EXPENSE_CATEGORIES` に含まれる | カテゴリを選択してください |
| `partner` | 非空（空白のみ不可）、100 字以内 | 取引先を入力してください（100 字以内） |
| `memo` | 200 字以内 | メモは 200 字以内で入力してください |
| `file` | ちょうど 1 件 | 証憑ファイルを 1 つ添付してください |
| `file` | 拡張子（小文字化）が `EXPENSE_ALLOWED_EXTENSIONS`。`filetype` と `name` の**両方**で判定 | jpg / jpeg / png / heic / pdf のいずれかを添付してください |
| `file` | `size <= EXPENSE_MAX_FILE_BYTES` | ファイルは 10MB 以内にしてください |
| `file` | `url_private` のホストが `SLACK_FILE_ALLOWED_HOSTS` | 添付ファイルを認識できませんでした |

🔄 初版からの変更:

- **金額の上限 9,999,999 円を撤廃**。要件定義に無い独自制限だった（§7 #E7）
- **`edoc_confirm` の条件付き必須を削除**（§7 #E1）
- **`partner` は空白のみを不可**にする（Sheets 上で空セルと区別できないため）
- **`url_private` のホスト検証を Worker でも行う**（GAS 側でも再検証する。多層防御）
- 🔄 **日付の形式・実在チェックを追加**（判定順は「空 → 形式・実在 → 未来日」）。判定は `shared/src/time.ts` の `isValidDateString` に置き、**Worker と GAS が同じ関数を使う**。同じ判定を 2 箇所に書くと片方だけ直る事故が起きる
- 🔄 **エラーメッセージは `shared` の定数からテンプレートリテラルで生成する**（定数を変えたときにメッセージが取り残されるのを防ぐ）。体裁は本表の文言に合わせ、数字と単位の間に半角スペースを入れる

### 4.4 Sheets 数式インジェクション対策 🔄

`partner`・`memo` は利用者入力がそのまま Sheets のセルに入る。**`=` `+` `-` `@` で始まる文字列は
Sheets が数式として解釈する**ため、GAS 側で書き込む直前に先頭へ `'`（アポストロフィ）を付けて
テキストとして固定する。判定と付与は `core` の純関数 `escapeSheetFormula(s)` に置きテストする。

### 4.5 冪等キーと既存コードの更新 🔄

MVP 設計 §4.2 のモーダル送信規則をそのまま使う: `${view_id}:${sha256hex(JSON.stringify(view.state.values)).slice(0,16)}`。

**あわせて更新が必要な既存コード**（初版の見落とし）:

| ファイル | 変更 |
|---|---|
| `worker/src/journal.ts:33` | `InsertJournalInput.kind` の union に `'expense_submit'` を追加 |
| `shared/src/protocol.ts` | `GasRequest` union に追加。`CommandSource` 等と同様に `ExpenseSubmitSource` を定義 |
| `worker/src/slack/parse.ts` | `SlackStateValue` に `file_input` の `files` を追加（実際の形は S3 で確定） |
| `gas/src/app/validateRequest.ts` | `isGasRequest` に `expense_submit` の型ガードを追加 |
| `shared/package.json` | `exports` に `./expense` を追加 |

D1 の SQL 変更は**不要**（`journal.kind` は `TEXT` で `CHECK` 制約が無い）。

## 5. GAS の設計

### 5.1 経費台帳の列（MVP 設計 §7.1 から**変更**）

```
証憑ID | 証憑区分 | 日付 | 金額 | 取引先 | カテゴリ | メモ | Driveリンク | ファイルハッシュ
      | 元MIME | サイズ | 入力日時 | 処理状態 | MF仕訳ID
      | idempotency_key | slack_file_id | drive_file_id | 元ファイル名 | last_error | state_updated_at
      | 税区分 | 事業使用割合 | 訂正元証憑ID | 訂正理由
```

**MVP の 14 列に 10 列を追加する。** 🔄 初版の 4 列から増やした。

| 列 | 追加理由 |
|---|---|
| `idempotency_key` | **これが無いと再送で二重登録される。**生ログと同じ方式（MVP 設計 §4.2） |
| `slack_file_id` | 元ファイルの特定・再取得 |
| **`drive_file_id`** 🔄 | **Drive 側の存在確認に必須。**リンク文字列では削除・移動を検出できない（§5.6） |
| **`元ファイル名`** 🔄 | 監査時に「何を受け取ったか」を残す。Drive 上の名前は規約で付け替えるため |
| **`last_error`** 🔄 | システムエラーを `メモ`（利用者入力）に混ぜない |
| **`state_updated_at`** 🔄 | 停滞行の検出。`入力日時` だけでは最後にいつ進んだか分からない |
| `税区分` | 要件定義 §4.3.1 の任意項目。列のみ用意 |
| `事業使用割合` | 同上。**既定 100**（§7 #E5） |
| **`訂正元証憑ID`** 🔄 | 訂正・取消フロー（§5.7） |
| **`訂正理由`** 🔄 | 同上 |

- `処理状態 ∈ RECEIVED | FILE_SAVED | COMPLETED | ERROR | CORRECTED | VOID`
- 🔄 **システム列（`idempotency_key`〜`state_updated_at`）は保護し、既定で非表示にする。**
  手編集されると冪等性と監査証跡が壊れる
- 🔄 **列追加は「不足列を末尾に足す」汎用マイグレータを作らない。**
  既存ヘッダーが MVP の 14 列と**完全一致**することを確認 → xlsx バックアップを促す →
  一度きりのバージョン付き移行として追加する。不一致なら**何もせず中断**して手順書へ誘導する（fail closed）

### 5.4 ユースケース `handleExpenseSubmit`（🔄 全面改訂）

**初版の致命的な問題は 2 つあった。** (a) Drive 保存後に台帳更新が失敗すると再送で重複ファイルができる、
(b) 10MB の I/O をグローバルロック内で行い本番の打刻を止める。両方を解く形に作り直す。

```
【フェーズ 1】短いロック — 受付と再開点の決定
withLock:
  row = findExpenseByIdempotencyKey(key)
  ├─ row.処理状態 == COMPLETED           → return {ok:true, applied:false, reason:'DUPLICATE'}
  ├─ row.処理状態 ∈ {ERROR, VOID}        → return {ok:false, error: row.last_error, retryable:false}
  ├─ row 有り（RECEIVED / FILE_SAVED）   → 再開。証憑 ID を引き継ぐ
  └─ row 無し → validateExpenseInput() → 証憑 ID 採番（receipt_seq）→
       appendExpense({メタデータ, 処理状態:'RECEIVED', state_updated_at: now})
  resume = row.処理状態

【フェーズ 2】ロック外 — 重い I/O（ここが長い。ロックを持たない）
if resume == 'RECEIVED':
  { bytes, contentType } = slackFiles.download(url_private)   // ホスト検証つき
  実サイズ・Content-Type・マジックバイトを検証（不一致 → FILE_INVALID / FILE_TOO_LARGE）
  hash = digest.sha256Hex(bytes)
// resume == 'FILE_SAVED' ならダウンロード不要（すでに保存済み）

【フェーズ 3】短いロック — 状態再確認 → Drive → 確定
withLock:
  row = getExpenseByReceiptId(receiptId)              // フェーズ 2 の間に進んだ可能性を再確認
  if row.処理状態 == 'COMPLETED' → return DUPLICATE
  if row.処理状態 == 'RECEIVED':
     existing = drive.findByName(folderPath, filename)   // ★ 保存前に必ず検索する
     ├─ 0 件            → info = drive.saveFile(...)
     ├─ 1 件かつサイズ一致 → info = existing[0]（再利用。保存しない）
     └─ それ以外         → 処理状態='ERROR', last_error → return DRIVE_CONFLICT (retryable:false)
     updateExpense(receiptId, { drive_file_id: info.id, Driveリンク: info.url,
                                ファイルハッシュ: hash, 元MIME, サイズ,
                                処理状態:'FILE_SAVED', state_updated_at: now })
  全必須項目の充足を検証 → updateExpense(receiptId, { 処理状態:'COMPLETED', state_updated_at: now })
return {ok:true, applied:true}
```

**なぜこれで冪等になるか**

ファイル名には**その台帳行にしか割り当てられない証憑 ID** が含まれる（§5.5）。したがって
`folderPath` に同名ファイルがあれば、それは**この行の過去の試行が作ったもの以外にありえない**。
「Drive 保存は成功したが直後に落ちた」場合も、再送時のフェーズ 3 で 1 件見つかり**再利用**されるため、
**Drive への書き込みは高々 1 回**になる。初版の「稀な競合は週次で検出する」は事後検知であって
冪等性の保証ではなかった。

> サイズ一致は同一性の証明ではない（同サイズの別ファイルはありうる）。しかし証憑 ID がファイル名に
> 入っている以上、別内容の同名ファイルは「過去の試行で別のバイト列を保存した」場合しか起こらず、
> それは異常として `DRIVE_CONFLICT` で人手に回すのが正しい。Drive から読み戻してハッシュ比較する
> コストは、この規模では見合わない。

**ロック保持時間**

| 区間 | ロック | 概算 |
|---|---|---|
| フェーズ 1 | 保持 | Sheets 読み書き数回（< 1 秒） |
| フェーズ 2（ダウンロード＋ハッシュ） | **保持しない** | 10MB で数秒〜十数秒 |
| フェーズ 3（Drive 保存＋台帳更新） | 保持 | 10MB の Drive 書込（要 S4 実測） |

フェーズ 3 も Drive 書込を含むためゼロではないが、**打刻が待たされる時間は `GAS_LOCK_WAIT_MS = 10` 秒の
内側に収まる必要がある**。S4 で実測し、超えるようなら業務上限を下げる。

**完了通知**: 本人へ DM で「✅ 経費を登録しました `R-20260901-001` / 2026-09-01 / ¥1,200 / 消耗品費 / ○○商店」＋ Drive リンク。
🔄 **DM 失敗を完全には握り潰さず**、`last_error` に記録して `処理状態` は `COMPLETED` のままにする
（利用者が「登録されていない」と誤解して二重入力する誘因を残さないため、週次照合で通知漏れを報告する）。

🔄 `validateExpenseInput` は**フェーズ 1 の台帳追記より前**に呼ぶ（初版は呼ぶ順序が書かれていなかった）。

**`date` の検証は「空 → 形式・実在 → 未来日」の順で行う**（2026-08-31 の WP7 レビューで追記）。
`datepicker` が形式を保証することを前提にしてはならない。この関数は「Worker を信用しない」ための
層であり、**Cron 再送で古い・壊れたペイロードが到達する経路がある**。

| 判定 | メッセージ |
|---|---|
| 空 | 日付を選択してください |
| `YYYY-MM-DD` 形式でない、または**実在しない日付**（月 01–12、日はその月の実日数、うるう年考慮） | 日付を選択してください（形式専用の新しい文言は作らない） |
| `> todayJst` | 未来の日付は登録できません |

> **なぜ必要か**: 形式検証が無いと `date="2026-00-99"` が**全検証を素通りし**、
> `receiptFolderPath` が `経費証憑/紙/2026/00` という実在しない月のフォルダを作り、
> `makeReceiptId` が `R-20260099-001` という不正な証憑 ID を台帳に永久に残す。
> また文字列比較の偶然で `"not-a-date"` が「未来の日付」と誤判定される。
> うるう年判定は**`Date` のパースに頼らず純関数で自前に書く**（環境依存の緩さを避けるため）。

### 5.6 週次の突合（`trigWeeklyOrphanCheck`）🔄 全面簡素化

初版の「直近 8 日のファイル名だけを見る差分検査」では、`COMPLETED` 後の削除・差替え、
トリガーの長期停止、リンク切れを検出できなかった。**月数件〜数十件の規模なら全件走査で足りる**ため、
差分ロジックを捨てて単純化する。

| 関数 | 時刻 | 処理 |
|---|---|---|
| `trigWeeklyOrphanCheck` | 毎週月曜 07 時台 | 台帳**全件**について下記を検査し、1 件以上あればチャンネルへ投稿。完了時に内部 `expense_scan/last_success_at` を更新 |

1. **停滞行**: `処理状態 ∉ {COMPLETED, VOID, CORRECTED}`。`state_updated_at` からの経過も添える
2. **消えた証憑**: `drive_file_id` を `drive.getById()` で引き、`null` または `trashed: true`
3. **サイズ不一致**: Drive 上の現在のサイズが台帳の `サイズ` と違う（差し替えの検出）
4. **通知漏れ**: `処理状態 == COMPLETED` かつ `last_error` に DM 失敗が残っている行
5. **前回実行からの経過**: `last_success_at` が 8 日以上前ならその旨も報告（**トリガー停止の自己検出**）

### 5.7 訂正・取消フロー 🔄 新設

`COMPLETED` 後に金額・取引先・区分の誤りが判明した場合、**システム列を直接上書きしない**
（監査証跡とハッシュの意味が失われる）。生ログの `CORRECTION` 方式に揃える。

- **訂正**: 正しい内容で `/keihi` から**新しい行を登録**し、旧行の `処理状態` を `CORRECTED`、
  新行の `訂正元証憑ID` に旧証憑 ID、`訂正理由` を記入する。Drive の旧ファイルは**削除しない**
- **取消**（誤登録・重複）: 旧行の `処理状態` を `VOID`、`訂正理由` を記入する
- MVP 期間は**シート上の手作業**で行い、手順を runbook に書く。専用モーダルは作らない（利用者 1 名・低頻度のため）
- `MF仕訳ID` 記入時に `CORRECTED`/`VOID` 行を除外することを運用手順に明記する

### 5.8 `dispatch` の変更 🔄

`gas/src/app/dispatch.ts` は現在**全ルートを `ports.lock.withLock()` で包んでいる**。
`expense_submit` はユースケース内で自前にロックを分割するため、**`expense_submit` だけロック外で
`routeRequest` に渡す**ように分岐を変える。既存 4 種の挙動は変えない。

## 6. 電帳法・コンプライアンス上のゲート（**実装前に必ず解消する**）

| # | ゲート | 状態 |
|---|---|---|
| G-1 | **電子取引データの事務処理規程を備え付ける**（国税庁ひな形ベース）。🔄 規程だけでなく、**訂正・削除の実際の手順、責任者、対象データ、運用記録**まで含める | ⬜ 未着手（`docs/未決事項・デプロイ前確認.md` §3 #9） |
| G-2 | 証憑・帳簿の保存期間（5 年／7 年）を税理士に確認。🔄 **起算日を規程に明記し、自動削除は実装しない** | ⬜ 回答待ち |
| G-3 | 法定帳簿の「正」は MF、Sheets は補助簿。月次合算仕訳の可否を税理士に確認 | ⬜ 回答待ち |

**紙証憑の扱い**: 紙原本を法定保存し、撮影画像を業務上の補助とする運用は適法。スキャナ保存制度は
「紙をスキャンしたデータを**紙原本に代えて**保存する制度」であり、**紙を廃棄せず画像を原本の代替と
主張しない限り**、撮影しただけで同制度へ移行するわけではない。運用規程に
**「紙証憑は紙が原本」「画像は補助」「保存期間満了まで紙を廃棄しない」**と明記する。

> 🔄 初版は「スキャナ保存にはタイムスタンプや外部サービス契約が必須」と書いていたが、これは不正確。
> 訂正・削除履歴を確認でき時刻を客観的に証明できるシステムならタイムスタンプを省略できる場合がある。
> ただし現在の Sheets ＋ Drive 構成がその要件を満たすとは考えにくく、**スキャナ保存を採用しない結論自体は妥当**。

## 7. 要件定義 v1.1 からの差分（実装上の決定）

| # | 項目 | 決定 | 理由 |
|---|---|---|---|
| **E1** 🔄 | 「電子取引＋画像」の確認警告 | **撤回した。**警告もチェックボックスも設けない。`hint` で原本優先を案内するのみ | 初版は「スクリーンショットは電子取引の保存として認められない」を前提にしていたが、**この法令解釈が誤り**だった。国税庁一問一答【電子取引関係】問 36 は「ウェブサイト上に表示される領収書をスクリーンショットし、サーバ等に保存する」「いわゆるスクリーンショットによる領収書の画像データでも構いません」と**明示的に認めている**。認められないのは「電磁的記録を保存せず取引情報のみを自ら入力すること」。初版のままでは Web でしか表示されない**適法な電子取引証憑を拒否**していた。要件定義 §4.3.1 も同時に訂正した。<br>なお初版が挙げた「`response_action` は `errors`/`clear` の二択」という理由も誤り（`update`/`push` がある） |
| **E2** 🔄 | 処理状態と処理順 | 台帳行を**先に**作り、`RECEIVED → FILE_SAVED → COMPLETED`／`ERROR`／`CORRECTED`／`VOID`。**状態別の再開点と Drive の保存前検索**を必須とする（§5.4） | 台帳先行という方向は正しかったが、初版は再開点を定義しておらず、**Drive 保存後に落ちると重複ファイルができた**。保存前に `findByName` で検索して再利用することで初めて冪等になる |
| **E3** | 証憑区分の初期値 | 推定値を初期選択にしない | 区分は保存義務の分岐そのもの。無自覚な確定を避ける |
| **E4** | 非同期失敗時の再実行ボタン | 設けない。`retryable:true` は Cron が自動再送、`retryable:false` のみ DM | MVP の D1＋Cron で at-least-once を実現済み。ボタンは Cron と競合し無効打になる。**ただし §3.2 のエラー分類と、DM 文面での「`/keihi` からやり直す」案内を必須とする** |
| **E5** 🔄 | 事業使用割合 | **モーダルには出さないが、列の既定値を `100` とし、月次の確認手順を runbook に必須項目として書く** | 初版は「免税事業者なので使わない」としたが**理由が誤り**。事業使用割合は消費税ではなく**所得税の家事按分**に関わるため、課税・免税とは無関係に必要になりうる。一方で経費の大半は 100% であり全件入力させるのは負担が大きい。既定 100＋月次確認で両立させる |
| **E6** | システム列の追加 | `idempotency_key`・`slack_file_id`・`drive_file_id`・`元ファイル名`・`last_error`・`state_updated_at` を追加し、**保護・非表示**にする | at-least-once 配送と突合に必須。要件定義の 14 列のままでは再送で二重登録される |
| **E7** 🔄 | 金額の上限 | **撤廃した**（初版は 9,999,999 円を上限にしていた） | 要件定義に無い独自制限だった。桁誤りの検出が必要なら別途承認を得てから入れる |

## 10. リリース・ロールバック手順 🔄

プロトコル追加は Worker と GAS の**同時整合**を要する。順序を誤ると pending が処理できなくなる。

### 10.1 デプロイ順

1. `ENABLE_EXPENSE=0`・`ENABLE_E_DOC=0` で開始
2. **スプレッドシートを xlsx でバックアップ**
3. **GAS を先にデプロイ**（`expense_submit` を受け取れる後方互換実装＋列移行）。`clasp push` 後に
   **`clasp create-deployment --deploymentId <既存 ID>` が必須**（`docs/runbooks/02_運用・再デプロイ.md` §B）
4. Worker をデプロイ
5. 疎通試験（`/keihi` でモーダルが開く。まだ `ENABLE_EXPENSE=0` なので送信は拒否される）
6. `ENABLE_EXPENSE=1` にして**紙証憑のみ**で受入試験
7. **G-1〜G-5 完了後**に `ENABLE_E_DOC=1`

GAS 再デプロイ中は停止フラグ（`forwarding_enabled=0`）を使う。

### 10.2 ロールバック

**pending の `expense_submit` が残っている間は旧 GAS へ戻さない**（旧 GAS は `BAD_REQUEST` を返し、
`retryable:false` で `rejected` になって記録が失われる）。

- まず `ENABLE_EXPENSE=0` にして新規受付を止める
- D1 の `pending` かつ `kind='expense_submit'` が 0 件になるまで待つ
- そのうえで GAS → Worker の順に戻す

### 10.3 受入試験（`docs/受入試験チェックリスト.md` に追加）

- `/keihi` → モーダルが開く。証憑区分は未選択
- 必須項目を空で送信 → モーダルが閉じず該当ブロックに日本語エラー
- 未来日 → エラー。11MB → エラー
- **`=SUM(A1:A2)` を取引先に入力 → 台帳にテキストとして入る（数式にならない）**
- 正常送信 → モーダルが閉じ、数秒後に DM で証憑 ID と Drive リンク
- Drive に `経費証憑/紙/2026/09/20260901_1200円_○○商店_R-20260901-001.jpg` が存在する
- 台帳が `COMPLETED`、`ファイルハッシュ`・`drive_file_id` が入っている
- **GAS 停止中に送信 → 台帳に行が増えない → 再開後 Cron 再送で 1 行だけ増える**
- 同じモーダルを二重送信 → 台帳は 1 行のまま
- **Drive にファイルを残したまま台帳の `処理状態` を `RECEIVED` に戻して再送 → Drive のファイルが増えず、既存が再利用される**（冪等性の中核）
- ファイルを削除してから再送 → `ERROR`、DM でエラー、`/keihi` からやり直せる
- **10MB のファイル登録中に打刻 → 打刻が `LOCK_TIMEOUT` にならない**（ロック分割の確認）
- `trigWeeklyOrphanCheck` を手動実行 → 停滞行・消えた証憑・サイズ不一致が検出される

# Runbook 02: 運用・再デプロイ

初回デプロイ後の日常運用。

---

## A. Worker（Cloudflare）を再デプロイする

コード変更・設定変更を反映する。Worker はステートレス（正データは D1 と Sheets）なので停止フラグは不要。

```
! npm run -w @kadobo/worker test && npm run -w @kadobo/worker typecheck
! cd /Users/takenouchiharuhi/projects/kadobo/worker && npx wrangler deploy
```

- マイグレーションを追加した場合は先に `npx wrangler d1 migrations apply DB --remote`。
- シークレット更新は `npx wrangler secret put <NAME>`（即時反映・再デプロイ不要）。

✅ 確認: `/kado` でカードが再表示される。

## B. GAS を再デプロイする（停止フラグ運用）

> **重要**: `clasp push` は HEAD（ソース）を更新するだけで、`/exec`（バージョン固定のウェブアプリデプロイ）には反映されない。
> push 後に必ず既存デプロイを新バージョンへ更新すること:
> ```
> npx clasp deployments                       # 対象の deploymentId（@番号付き・URL と一致）を確認
> npx clasp create-deployment --deploymentId <DEPLOYMENT_ID> --description "<変更内容>"
> ```
> これで `/exec` URL は変わらず、最新コードが配信される。

GAS の再デプロイ中は一時的に doPost が不安定になり得る。**打刻を失わないため**、
デプロイ中は Worker の転送を止める（止めている間の打刻は D1 に pending で溜まり、
再開後に Cron が自動再送するのでユーザーの押し直しは不要）。

1. **転送停止**:
   ```
   ! cd /Users/takenouchiharuhi/projects/kadobo/worker && npx wrangler d1 execute DB --remote --command "UPDATE settings SET value='0' WHERE key='forwarding_enabled'"
   ```
2. **ビルド＆プッシュ＆再デプロイ**:
   ```
   ! cd /Users/takenouchiharuhi/projects/kadobo && npm run build
   ! cd /Users/takenouchiharuhi/projects/kadobo/gas && npx clasp push
   ```
   GAS エディタ → **デプロイ → デプロイを管理 → 既存のウェブアプリデプロイを編集 → バージョン=新しいバージョン → デプロイ**。
   ※ `/exec` URL を変えないため「新規デプロイ」ではなく**既存デプロイの編集**を使う。URL が変わってしまった場合は ⑥ の手順で Worker の `GAS_URL` を更新。
3. **転送再開**:
   ```
   ! cd /Users/takenouchiharuhi/projects/kadobo/worker && npx wrangler d1 execute DB --remote --command "UPDATE settings SET value='1' WHERE key='forwarding_enabled'"
   ```
4. 再開後、溜まっていた pending は 5 分周期の Cron が `action_ts` の時刻どおり再送する。すぐ流したい場合は `/kado` などで動作確認。

✅ 確認: 停止中に打刻 → カードが「⚠️ 記録待ち」→ 再開後に「✅」へ変わる。

## D. シークレットのローテーション

| 対象 | 手順 |
|---|---|
| Slack Bot Token 再発行時 | Slack で再発行 → `wrangler secret put SLACK_BOT_TOKEN` かつ GAS Script Property `SLACK_BOT_TOKEN` を更新（両方） |
| Slack Signing Secret | `wrangler secret put SLACK_SIGNING_SECRET` |
| `GAS_SHARED_SECRET` | 新値を `openssl rand -hex 32` で生成 → **Worker と GAS の両方**を同時に更新（片方だけだと封筒検証が失敗し全打刻が pending 化する）。B の停止フラグを併用すると安全 |

## E. 月次締め（MVP は手動）

MVP では請求書作成の自動化（MF 連携）は未実装。毎月:
1. 前月の **日次集計** に `要修正` が無いことを確認（`trigMonthly` が毎月 1 日 06 時台に要修正一覧と月合計をチャンネルへ投稿する）。
2. **月次請求** シートの当月行（`worked_minutes`・`hours`・`amount` 等）を確認。
3. 内容を確定したら当該行の `state` を手で `LOCKED` にする（以降その月への修正は拒否され DM 通知される）。
4. `amount`・`tax_amount`・`withholding_amount`・`net_amount` を MF クラウド請求書へ手動転記し、未送付で作成 → 画面で確認して送付。
5. 消費税相当額・源泉の扱いは `../未決事項・デプロイ前確認.md` の確定結果に従う。

## G. 定期通知の意味（自動）

| 通知 | いつ | 意味 |
|---|---|---|
| ⚠️ 記録待ち（カード） | 打刻直後に GAS 失敗（GAS が未適用と明言） | Cron が自動再送中。放置してよい |
| ⏳ 記録中…のまま（カード） | GAS の応答を確認できなかった | 適用有無が不明なため Worker は意図的にカードを触らない。Cron 再送（最大 5 分）で復旧。急ぐなら `/kado` |
| ⚠️ 記録の反映を確認できませんでした（本人だけに見える ephemeral） | 同上 | 上と同じ。自動再試行される |
| ⚠️ 記録に失敗しました（カード） | GAS が `retryable:false` で拒否 | 再送されない。DM のエラー内容を確認し 03 を参照 |
| `<@you>` メンション（チャンネル） | 同一 pending が約 6 時間失敗継続 | GAS/接続に問題。03 を参照 |
| 「稼働中のまま」DM/メンション | 22 時台トリガー | 終了の押し忘れ。修正ボタンで終了時刻を入力 |
| 「要修正」一覧 | 月初トリガー | ペアリング不能な日。修正モーダルで直す |

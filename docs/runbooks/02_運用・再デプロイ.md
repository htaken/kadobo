## B. GAS を再デプロイする（停止フラグ運用）

> **重要**: `clasp push` は HEAD（ソース）を更新するだけで、`/exec`（バージョン固定のウェブアプリデプロイ）には反映されない。
> push 後に必ず既存デプロイを新バージョンへ更新すること:
> ```
> npx clasp deployments                       # 対象の deploymentId（@番号付き・URL と一致）を確認
> npx clasp create-deployment --deploymentId <DEPLOYMENT_ID> --description "<変更内容>"
> ```
> これで `/exec` URL は変わらず、最新コードが配信される。
> **`clasp deployments` は 2 行返る。`@HEAD` の方ではなく、`@<番号>` が付いている方が対象。**
> 実績: 2026-09-27 に `AKfycbxn0CTW6BV4w92lfaBwREb8wYrfjCRhtdBuuVJSyHe35_7szrc-UDEs584w7AcME61c`
> を `@8` → `@9` へ更新（`npx clasp push --force` の後に上記 2 コマンド。GAS エディタ不要）。

GAS の再デプロイ中は一時的に doPost が不安定になり得る。**打刻を失わないため**、
デプロイ中は Worker の転送を止める（止めている間の打刻は D1 に pending で溜まり、
再開後に Cron が自動再送するのでユーザーの押し直しは不要）。

1. **転送停止**:
   ```
   ! cd /Users/takenouchiharuhi/projects/kadobo/worker && npx wrangler d1 execute DB --remote --command "UPDATE settings SET value='0' WHERE key='forwarding_enabled'"
   ```
2. **ビルド＆プッシュ＆再デプロイ**:
   ```
   ! cd /Users/takenouchiharuhi/projects/kadobo && npm run build
   ! cd /Users/takenouchiharuhi/projects/kadobo/gas && npx clasp push
   ```
   GAS エディタ → **デプロイ → デプロイを管理 → 既存のウェブアプリデプロイを編集 → バージョン=新しいバージョン → デプロイ**。
   ※ `/exec` URL を変えないため「新規デプロイ」ではなく**既存デプロイの編集**を使う。URL が変わってしまった場合は ⑥ の手順で Worker の `GAS_URL` を更新。
3. **転送再開**:
   ```
   ! cd /Users/takenouchiharuhi/projects/kadobo/worker && npx wrangler d1 execute DB --remote --command "UPDATE settings SET value='1' WHERE key='forwarding_enabled'"
   ```
4. 再開後、溜まっていた pending は 5 分周期の Cron が `action_ts` の時刻どおり再送する。すぐ流したい場合は `/kado` などで動作確認。

## H. 経費: 週次突合の読み方と訂正・取消の手順（実装設計 経費フェーズ §5.6・§5.7）

### H.1 週次突合（`trigWeeklyOrphanCheck`）の読み方

毎週月曜 07 時台に経費台帳（全行）を走査し、以下の 5 種のいずれかが 1 件以上あればチャンネルへ
1 通で報告する。**0 件のときは投稿されない**（他の定期トリガーと同じ方針）。

| 通知の項目 | 意味 | 対処 |
|---|---|---|
| ⚠️ 停滞行 | `処理状態` が `COMPLETED`/`VOID`/`CORRECTED` のいずれでもない行（`RECEIVED`/`FILE_SAVED`/`ERROR`）。経過時間つき | `ERROR` なら DM のエラー内容を確認し `/keihi` からやり直す。`RECEIVED`/`FILE_SAVED` が長時間続く場合は Cron 再送が止まっていないか（Worker 側）を確認する |
| ⚠️ 消えた証憑 | 台帳の `drive_file_id` が Drive 上で見つからない、またはゴミ箱に入っている | 誤って削除・移動していないか確認する。復元できないなら該当行を H.2 の手順で `VOID` にし、必要なら証憑を再登録する |
| ⚠️ サイズ不一致 | Drive 上の現在のファイルサイズが台帳の `サイズ` と異なる（差し替えの疑い） | Drive 上のファイルが意図した差し替えか確認する。誤った差し替えなら復元し、正しい差し替えなら台帳の `サイズ`・`ファイルハッシュ` を実態に合わせて手修正する |
| ⚠️ 通知漏れ | `処理状態` は `COMPLETED`（登録自体は成功）だが `last_error` に `DM_FAILED:...` 等が残っている | 登録内容自体は正しいので急ぎの対応は不要。本人へ内容を共有し、必要なら該当行の `last_error` を手で消してよい |
| ⚠️ 前回の正常完了から N 日経過 | `expense_scan/last_success_at`（内部シート）が 8 日以上前 | 週次トリガーが止まっている可能性が高い。GAS のトリガー設定（「トリガー」画面）で `trigWeeklyOrphanCheck` が有効か確認し、必要なら `installTriggers()` を再実行する |

### H.2 訂正・取消（MVP はシート上の手作業。専用モーダルは無い）

`COMPLETED` 後に金額・取引先・区分の誤りが判明した場合、**システム列を直接書き換えない**
（冪等性と監査証跡が壊れる）。生ログの `CORRECTION` 方式と同じ考え方で、旧行は残したまま
状態だけ変える。

> ⚠️ **事務処理規程 第 2 条（`docs/事務処理規程_電子取引.md`）が求める記録は別にある**。
> 下記の経費台帳の状態変更だけでは、規程第 2 条が求める 8 項目のうち「申請日」
> 「訂正・削除日付」「訂正・削除内容」が記録されない。**訂正・取消を行うたびに、必ず
> 「訂正削除申請」シート（`setupSpreadsheet` が自動生成。手記入・保護なし）へ 8 項目を
> 記入すること。省略できない。**手順は本節末尾を参照。

> ⚠️ **列の位置に注意**: 経費台帳は 24 列（証憑ID〜訂正理由）。**15〜20 列目
> （`idempotency_key`／`slack_file_id`／`drive_file_id`／`元ファイル名`／`last_error`／
> `state_updated_at`）はシステム列としてシート保護・既定非表示になっており、GAS だけが更新する。
> 手編集してよいのは業務列（`処理状態` は 13 列目、`訂正元証憑ID` は 23 列目、`訂正理由` は
> 24 列目など）だけ。

**訂正**（金額・取引先・区分などの誤り）:
1. 正しい内容で `/keihi` から**新しい行を登録**する。
2. 旧行の `処理状態`（13 列目）を `CORRECTED` に書き換える。
3. 新行の `訂正元証憑ID`（23 列目）に旧行の証憑ID、`訂正理由`（24 列目）に理由を記入する。

**取消**（誤登録・重複登録）:

3. Drive 上のファイルは削除しない。

## I. 経費フェーズのロールバック（実装設計 経費フェーズ §10.2）

プロトコル追加は Worker と GAS の同時整合を要する。**pending の `expense_submit` が残っている間は
旧 GAS へ戻さない**（旧 GAS は `expense_submit` を認識できず `BAD_REQUEST` を返し、
`retryable:false` で `rejected` になって記録が失われる）。

> ⚠️ **「pending が 0 件」はロールバック完了の十分条件ではない。** 次のいずれでも pending は
> 0 に近づきうるが、意味がまったく違う:
> - `forwarding_enabled=0` のままだと、Cron は転送自体を止めているだけで GAS 側の状況とは
>   無関係に pending は減らない（そのまま溜まり続ける）。GAS や Drive の障害が続いていても
>   同様に減らない
> - 一方、`FILE_NOT_FOUND`／`FILE_FORBIDDEN`／`CONFIG_MISSING` 等の非再試行エラーで
>   `rejected` になった場合も pending は 0 に近づくが、**その行の証憑は保存されずに終わって
>   いる**（`rejected`＝「記録が消えた」わけではなく、経費台帳には `処理状態=ERROR` の行が
>   残る）。
>
> したがって「pending=0」を見ただけで安全とみなさず、必ず 3〜4 の確認を行うこと。

1. **Worker 側だけ**を先に無効化する（GAS 側の `ENABLE_EXPENSE` はまだ落とさない。§5.9.3）:
   ```
   npx wrangler d1 execute DB --remote --command "UPDATE settings SET value='0' WHERE key='enable_expense'"
   ```
   ⚠️ この書き込みは冒頭の注意のとおり、本人が自分で実行すること。
2. **排出中の前提を確認する**: `forwarding_enabled=1` であること、GAS 側の対象フラグ
   （通常のロールバックなら `ENABLE_EXPENSE`、`e_doc` だけ止めるなら `ENABLE_E_DOC`）が
   **まだ有効なまま**であることを先に確認する（これらが無効のままだと pending は Cron で
   捌かれない）:
   ```
   ! cd /Users/takenouchiharuhi/projects/kadobo/worker && npx wrangler d1 execute DB --remote --command "SELECT key, value FROM settings WHERE key IN ('forwarding_enabled','enable_expense','enable_e_doc')"
   ```
3. **pending の `expense_submit` が 0 件になるまで待つ**（通常のロールバックは全件、`e_doc` だけ
   止める場合は**電子取引の pending だけ**を対象にする。`paper` の pending が 0 でも `e_doc` の
   ロールバック判断には使えない）:
   ```
   -- 通常（enable_expense 全体のロールバック）
   ! cd /Users/takenouchiharuhi/projects/kadobo/worker && npx wrangler d1 execute DB --remote --command "SELECT COUNT(*) AS pending_expense FROM journal WHERE status='pending' AND kind='expense_submit'"

   -- e_doc だけを止める場合（payload の receipt_type で絞る）
   ! cd /Users/takenouchiharuhi/projects/kadobo/worker && npx wrangler d1 execute DB --remote --command "SELECT COUNT(*) AS pending_edoc FROM journal WHERE status='pending' AND kind='expense_submit' AND payload LIKE '%\"receipt_type\":\"e_doc\"%'"
   ```
   `pending_expense`（または `pending_edoc`）が `0` になるまで、Cron 周期（5 分）おきに確認する。
   **減らないとき**は放置せず、`attempts`・`last_error` を確認して原因を復旧する
   （`03_トラブルシューティング.md` 症状1の「pending の滞留」を確認する手順を参照。まず 2 のフラグが
   意図どおりか、GAS が例外を返し続けていないかを疑う）。
4. **0 になったら、対象期間の `rejected` 行を経費台帳と突き合わせる**（`rejected`＝pending が
   消えたことと、証憑が正しく保存し終わったことは別問題であるため）:
   ```
   -- 1 の無効化を開始した時刻（ms）以降に rejected になった expense_submit を列挙

   経費台帳側で `処理状態` が `COMPLETED`／`VOID`／`CORRECTED` **以外**の行（`RECEIVED`／

5. **受付判定と D1 INSERT の間の競合窓に対処する**: Worker の `view_submission` は
   「フラグを読む」→「（有効なら）検証・冪等キー生成・D1 INSERT」という順で処理しており、
   この 2 ステップは原子的ではない。そのため、`enable_expense=0` にした**直後の一瞬**に
   始まっていた送信が、フラグを `1` の状態で読んだまま INSERT まで進む窓が理論上ある
   （その行は、GAS 側の `ENABLE_EXPENSE` がまだ有効なら通常どおり処理され、落としたあとなら
   `EXPENSE_DISABLED` で `rejected` になり、送信した本人には失敗の DM が届く。台帳に不完全な
   行が残ることはない）。この窓を実務上つぶすため、**`enable_expense=0`（または
   `enable_e_doc=0`）にしたあと 1 分以上あけて、3 の pending=0 確認を 2 回行う**
   （1 回目の確認直後に滑り込んだ受付を 2 回目で拾う）。
6. 2 回とも `0`（かつ 4 の突き合わせ）を確認できたら、GAS 側の Script Property
   `ENABLE_EXPENSE` を `0`（または行ごと削除）にする。
7. そのうえで、GAS → Worker の順にコードを旧バージョンへ戻す（§B・§A の手順に従う）。

`e_doc` だけを止めたい場合（電帳法ゲートの再点検等）は、同じ手順を `enable_e_doc`／
`ENABLE_E_DOC` に対して行う（3 の「電子取引の pending」クエリを使う。`paper` の受付は継続する）。

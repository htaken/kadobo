# 稼働記録・経費管理システム 要件定義 v1.0

作成日: 2026-08-27 ／ 対象: 個人事業主（開業日 2026-09-01 予定）の稼働記録・経費・請求業務

---

## 1. 目的・背景

- 時間単価ベースの業務委託（A社）における**請求根拠としての稼働記録**を、Slack操作だけで正確に残す
- 経費のレシート・台帳管理をSlackで完結させ、電子帳簿保存法（スキャナ保存）に適合させる
- 月次の請求書作成をマネーフォワード（MF）連携で半自動化する
- 本システムはあくまで**受託者自身の自己管理・請求根拠ツール**であり、委託元が指定・管理する勤怠システムではない（偽装請負リスク回避のため、名称は「勤怠」ではなく「稼働記録」とする）

## 2. スコープ

**対象:** 稼働時間の打刻・集計・単価計算／経費入力・レシート保存・経費台帳／MF請求書の下書き自動生成
**対象外（現時点）:** 複数クライアント同時対応の高度化、入金消込の自動化、確定申告書作成そのもの、A社側システムとの直接連携

## 3. システム構成

```
Slack（ボタン・モーダル）
   │  Request URL
   ▼
Cloudflare Worker  … 署名検証＋即時ACK（数ms）
   │  waitUntil() で非同期転送（共有シークレット付与）
   ▼
GAS Webアプリ … ビジネスロジック本体
   ├─▶ Google スプレッドシート（生ログ／集計／マスタ／経費台帳）
   ├─▶ Google Drive（レシート画像保存）
   ├─▶ Slack response_url（カード更新・通知）
   └─▶ MFクラウド請求書 API（月次・請求書下書き作成）
          └─（MF標準連携）→ MFクラウド会計に売上仕訳
```

採用理由: Workers は V8 isolate によりコールドスタートが実質ゼロで、Slack の 3 秒 ACK 制約を確実に満たす。GAS は Sheets/Drive に認証レスで接続できるため本体処理を担当。両者の分担で「即ACK→後追い処理」の Slack 推奨パターンを実現する。

## 4. 機能要件

### 4.1 稼働記録

- `/kado` コマンド（または平日朝の自動投稿）で #稼働記録 チャンネルに**当日の稼働カード**を投稿
- カードは状態機械: `未稼働 →[開始]→ 稼働中 ⇄[休憩/再開]⇄ 休憩中`、`稼働中 →[終了]→ 確定`
- ボタン押下ごとに `chat.update` でカード自体を書き換え、**現在状態・当日累計時間・その状態で有効なボタンのみ**を表示（二重打刻をUIで防止）
- 全イベント（開始・休憩入・休憩戻・終了）を生ログシートに追記: タイムスタンプ／種別／メモ
- **修正モーダル**: カードの「✏️ 修正」から当日ログの時刻修正が可能。修正時は元の値を別列に保全（請求根拠の証跡）
- **押し忘れ検知**: GAS 時間トリガー（22:00）で「稼働中のまま」を検知し、終了時刻入力ボタン付きでメンション通知

### 4.2 集計・単価計算

- スプレッドシートは4シート構成:
  1. **生ログ**（追記専用・手編集禁止）
  2. **日次集計**（ペアリングで実稼働時間算出、丸めルール適用）
  3. **単価マスタ**（単価／消費税扱い／源泉徴収有無／**適用開始日**列で改定履歴管理）
  4. **月次請求**（月合計時間 × 単価 → 請求額。MF請求書明細と1:1対応）
- 丸めルール（1分単位 or 15分切り捨て等）は **A社と書面合意の上で確定**（→ §7 要確認）

### 4.3 経費

- `/keihi` コマンドでモーダル表示: 日付／金額／カテゴリ（選択式: 通信費・消耗品費・旅費交通費・新聞図書費 等）／取引先／メモ／**レシート画像（file_input ブロック）**
- 送信後の処理（GAS）:
  - Slack `url_private` から bot トークン（`files:read` スコープ）で画像取得
  - Drive `/経費レシート/YYYY/MM/` に保存。ファイル名: `YYYYMMDD_金額円_取引先.jpg`
  - 経費台帳シートに1行追記（日付・金額・取引先・カテゴリ・Driveリンク）
- **電帳法適合の設計**（スキャナ保存）:
  - 検索要件: 台帳の日付・金額・取引先列で充足
  - 改ざん防止: 「訂正削除の防止に関する事務処理規程」を備付け（国税庁ひな形を利用）
  - 入力期限: 受領後速やかに入力する運用（最長 約2ヶ月＋7営業日以内）
- レシート原本管理の「正」は Drive＋台帳とし、MF側には月次で仕訳のみ登録（MFアプリでの二重撮影は不要）

### 4.4 請求（MF連携）

- 月末締め後、GAS トリガーが月次請求シートを読み、MFクラウド請求書 API で**下書きステータス**の請求書を作成（明細例: 「○月分業務委託料 ○○h × ¥X,XXX」）
- 作成完了を Slack 通知。**送付は必ず人間が確認して実行**（金額確定の最終責任は人間側）
- 請求書には日別明細（月次集計のPDF）を添付し、「受託者の自己記録に基づく請求」の建付けを維持
- 請求書→会計の標準連携により売掛金仕訳を自動計上（→ §7 要確認）。入金は銀行連携で消込

## 5. 非機能要件

- **応答性**: Slack への ACK は Worker が数ms で返却。GAS 側処理は 30 秒以内、結果は response_url で反映
- **セキュリティ**:
  - Slack 署名検証（signing secret / HMAC-SHA256）は **Worker 側**で実施
  - Worker → GAS 間は共有シークレットをヘッダー付与し GAS 側で検証（GAS URL の裸公開を防ぐ）
  - トークン類は Worker の環境変数（Secrets）／GAS の Script Properties に保存。コードに直書きしない
- **コスト**: 全構成が無料枠内で恒久運用可能な想定（Workers 10万req/日、GAS 無料、Slack 無料プランで Block Kit 可）
- **可用性・保全**: 生ログは追記専用。修正は履歴を残す。スプシは定期バックアップ（Drive 版管理で代替可）

## 6. 法令・制度要件

- **電子帳簿保存法**: §4.3 の通り（規程備付け・検索要件・入力期限）
- **インボイス制度**: 免税事業者のため適格請求書は発行不可。登録番号欄のない区分記載請求書を発行。消費税相当額の扱いは A社と契約時に合意
- **偽装請負回避**: ツールの名称・所有・運用はすべて受託者側。委託元の勤怠システムは使用しない。請求は自己記録ベース

## 7. 要確認事項（オープン項目）

| # | 項目 | 確認先 |
|---|------|--------|
| 1 | MFクラウド請求書 API が個人向けプランで利用可か・追加料金の有無 | MF デベロッパーサイト |
| 2 | 請求書→会計の自動仕訳連携の有効化条件・設定手順 | MF サポートページ |
| 3 | API レート制限（月1回作成なら実質影響なし、念のため） | API リファレンス |
| 4 | 丸めルール・締め日・支払サイト | A社と契約時に合意 |
| 5 | 源泉徴収の要否・消費税相当額の請求可否 | A社（＋業務内容の整理） |
| 6 | 事務処理規程の作成（国税庁ひな形ベース） | 自身で備付け |

## 8. フェーズ計画

| フェーズ | 内容 | 目標時期 |
|---|---|---|
| **MVP** | Worker＋GAS＋稼働カード＋4シート集計（請求書は手動転記） | 8月中に稼働開始 |
| **自動化** | MF請求書API下書き生成／経費モーダル＋レシート保存 | 9〜10月 |
| **仕上げ** | 月次サマリ自動投稿・押し忘れ検知強化・仕訳運用の定着 | 以降順次 |

## 9. 決定事項ログ

- 報酬体系: 時間単価ベース（時給×稼働時間）→ 稼働ログ＝請求根拠
- アーキテクチャ: **最初から Cloudflare Worker を前段に配置**（GAS 単体案は不採用）
- レシート管理: Slack モーダル＋Drive＋台帳を「正」とする（MFアプリ撮影との二重運用はしない）
- 請求書送付: 自動生成は下書きまで、送付判断は人間

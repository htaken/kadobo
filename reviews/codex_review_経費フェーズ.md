## 1. 総評

**このまま実装着手するのは不可です。** 特に、Drive 保存成功後の障害で添付ファイルが重複する冪等性の欠陥、電子取引のスクリーンショットを拒否する法令解釈、既存プロトコル／Cron と新設計の型不整合は、着手前に直す必要があります。  
一方、D1 受付ジャーナル、段階的な状態管理、紙原本と電子取引の区別という基本方針は妥当です。§5.4 を副作用後の再開に耐える設計へ改め、法令ゲートと運用手順を先に確定すれば実装可能です。

## 2. Blocker

### 1. Drive 保存の冪等性が成立していない

[§5.4 の処理順](/Users/takenouchiharuhi/projects/kadobo/docs/実装設計_経費フェーズ.md:281)では、既存行が `COMPLETED` 以外なら再びダウンロード・Drive 保存へ進みます。このため、少なくとも次の競合窓が残ります。

1. Drive 保存成功
2. `FILE_SAVED` への台帳更新が失敗
3. Cron 再送
4. 同じ名前でも Drive は重複ファイルを許すため、再度保存

さらに、`FILE_SAVED` の行自体も現状の記述では手順3から再開するため、台帳更新後・`COMPLETED` 更新前の障害でも再保存します。決定的なファイル名や受付IDは「検索しやすくする」だけで、重複作成を防ぐ一意制約ではありません。週次検査は事後検知であり、冪等性の保証にはなりません。

**修正案**

- 経費台帳に `drive_file_id`、`file_sha256`、`file_size` を保存する。
- 状態別に再開点を明示する。
  - `COMPLETED`: 成功扱いで終了
  - `FILE_SAVED`: Drive へ再保存せず、検証と `COMPLETED` 更新だけ行う
  - `RECEIVED`: 決定的ファイル名で既存ファイルを検索し、1件かつハッシュ一致なら再利用。0件だけ新規作成。複数件または不一致は自動処理を止める
- Drive 保存後に例外が返る曖昧なケースに備え、再試行時は必ず既存ファイルを検索する。
- 「保存副作用は成功したが例外」「`FILE_SAVED` 後に停止」「`COMPLETED` 応答消失」「同一キーの同時実行」を故障注入テストに入れる。
- ファイル検索契約を `listFileNames(): string[]` ではなく、ID・名前・作成日時・サイズ・trashed 状態を返すものへ変更する。

Drive の同名ファイル検索自体は `Folder.getFilesByName()` で可能です。[Apps Script Drive Folder リファレンス](https://developers.google.com/apps-script/reference/drive/folder)

### 2. #E1 の法令解釈が誤っており、正当な電子取引証憑を拒否する

[電子取引時の確認チェック](/Users/takenouchiharuhi/projects/kadobo/docs/実装設計_経費フェーズ.md:51)は「画面キャプチャではないこと」を条件付き必須にしています。しかし国税庁は、電子取引データについてファイル形式を限定しておらず、PDF 変換やスクリーンショットによる保存も認めています。

したがって、Web サイトやアプリでしか表示できない取引を拒否する、または利用者に事実と異なるチェックを要求する設計になります。これは法令上の安全策ではありません。

また、Slack モーダルの同期応答が `errors` と `clear` しかないという説明も誤りで、`response_action` には `update` と `push` もあります。

**修正案**

- 「スクリーンショットではない」チェックを廃止する。
- 代わりに「ダウンロード可能な原本がある場合は原本を保存する。Web／アプリ表示のみの場合は、日付・金額・取引先等が判読できる画面保存も可」と案内する。
- 確認を残すなら、単なるUI表示ではなく `edoc_source_kind` や `edoc_confirmed` として Worker→D1→GAS→台帳まで保存する。
- ファイル形式ではなく、取引情報の包含、可読性、変更・削除管理、検索・提示可能性を検査対象にする。

根拠は[国税庁「電子取引データ保存」教材](https://www.nta.go.jp/taxes/sake/hambai/moderutekisuto/pdf/r06_07_01.pdf)および[電子取引関係一問一答](https://www.nta.go.jp/law/joho-zeikaishaku/sonota/jirei/pdf/03-7.pdf)です。

### 3. 新プロトコルが既存 Cron／型契約と整合せず、そのままでは実装できない

新しい `expense_submit` は `channel_id` と `message_ts` を持ちませんが、既存 Cron は全 pending request に対して `original.channel_id` を参照しています。[cron.ts](/Users/takenouchiharuhi/projects/kadobo/worker/src/cron.ts:31)  
また、既存ジャーナルの `kind` 型に `expense_submit` がありません。[journal.ts](/Users/takenouchiharuhi/projects/kadobo/worker/src/journal.ts:33)

さらに、設計上の Drive ポートは名前の配列しか返さないのに、週次検査は「直近8日」「作成日時」「台帳との対応」を判定するとしています。現在の契約では実装不能です。

**修正案**

- `ExpenseSubmitRequest` に通知先を持たせるか、経費通知は `user_id` 宛てDM専用として Cron を分岐する。
- D1 の SQL 変更が不要でも、TypeScript の `kind` union、パーサー、シリアライザーを更新する。
- Drive ポートに `id/name/createdAt/size/trashed` を返す検索APIを追加する。
- GAS 側の検証を副作用前に明記する。現行 §5.4 は `validateExpenseInput` を呼ぶ順序が書かれていない。
- チェックボックスを保持するなら、その値もプロトコルに含める。
- `shared/src/expense.ts` を追加するだけでなく、package exports にも公開する。

## 3. 重要な指摘

### GAS のグローバルロック中に外部I/Oをしてはいけない

既存の dispatch は全ルートを `withLock` で包んでいます。[dispatch.ts](/Users/takenouchiharuhi/projects/kadobo/gas/src/app/dispatch.ts:60)  
この中で Slack ダウンロード、SHA-256、Drive 保存を行うと、最大10MBの処理中ずっとスクリプトロックを占有し、本番稼働中の打刻まで `LOCK_TIMEOUT` にします。

次の二段階に分けるべきです。

1. 短いロックで受付行の予約・現在状態確認
2. ロック外でダウンロードとハッシュ計算
3. 短いロックで状態再確認、Drive 保存／既存ファイル再利用、台帳更新

ただし、Drive 保存と台帳更新の原子的実行はできないため、Blocker 1 の再検索処理は別途必要です。[LockService リファレンス](https://developers.google.com/apps-script/reference/lock)

### Worker の時間・サブリクエスト見積もりが危険

Cloudflare Workers Free では、HTTP リクエストの CPU 時間は10ms、メモリは128MB、サブリクエストは50です。`waitUntil()` もレスポンス後に無制限には動かず、最大30秒です。[Cloudflare Workers Limits](https://developers.cloudflare.com/workers/platform/limits/)

設計の GAS タイムアウト25秒は、D1 結果更新やSlack通知にほぼ余裕がありません。20〜22秒程度に下げ、応答消失後も D1/Cron から回復できることを確認すべきです。

また、既存 Cron の「20件 × GAS redirect 2回＋通知でも50以内」という計算は誤りです。[cron.ts](/Users/takenouchiharuhi/projects/kadobo/worker/src/cron.ts:20)  
全件通知する最悪ケースは `20 × (2 + 1) = 60` です。バッチを16件以下にする、通知を集約する、または消費済みサブリクエスト数から動的に打ち切る必要があります。5分間隔 Cron の重複起動を防ぐ lease/claim も検討してください。

### Slack 周辺は概ね可能だが、ACK 経路を詰める必要がある

`file_input`、`files:read`、`url_private` への Bearer token 付きアクセスという方針自体は仕様に合っています。[file input element](https://docs.slack.dev/reference/block-kit/block-elements/file-input-element/)、[file object](https://docs.slack.dev/reference/objects/file-object/)

一方で、以下を修正してください。

- `/keihi` は `views.open` 完了を待ってからACKする必要はない。trigger は3秒で失効するため、直ちに開始し `waitUntil` に渡して200を返す構成を検証する。
- `view_submission` は3秒以内の同期応答が必須。D1 insert 失敗時は `clear` せず、モーダルにエラーを返す。
- `response_action` は `errors/clear` 以外に `update/push` もある。[Slack Modals](https://docs.slack.dev/surfaces/modals/)
- 「input 以外は `state.values` に載らない」という記述は正確でない。stateful block element の状態も submission に含まれる。ただし `file_input` は input block 内に置く必要がある。
- 受付 p95/p99 と D1 障害時の挙動を受入条件にする。[Handling user interaction](https://docs.slack.dev/interactivity/handling-user-interaction/)

### Slack Bot Token の漏えい対策が必要

GAS が受け取った任意の `url_private` に Bot Token を付けてアクセスできる設計は、将来パーサーや署名境界に欠陥が入った場合に SSRF／トークン漏えいになります。

- URL のホストを `files.slack.com` 等の許可ホストへ厳密に限定する。
- 可能なら GAS には Slack file ID だけ送り、Slack APIで最新メタデータとURLを取得する。
- Slackの申告サイズをダウンロード前にも検査し、実際のレスポンスサイズ・Content-Type・マジックバイトも検証する。
- 401/403 は設定・権限エラー、404 は恒久エラー、429 は `Retry-After` に従う、5xx は一時エラーとして分類する。「その他4xxをすべて再試行」は避ける。

### GAS の10MB処理はハード上限内だが、実機スパイクが必要

Apps Script は通常1実行6分、URL Fetch のレスポンス上限は50MBなので、10MBは公表上限内です。[Apps Script quotas](https://developers.google.com/apps-script/guides/services/quotas)

ただし以下は未検証です。

- `Utilities.computeDigest` の入力は JavaScript の byte array であり、設計上の `Uint8Array` とそのまま一致しない。
- 10MB取得→byte array→digest→Blob→Drive保存で、一時的に複数コピーがメモリに存在する。
- Apps Script の実用メモリ上限は公式に明示されていないため、成功を仕様から断定できない。

10MB JPEG／PDF／HEICで、実行時間・ヒープ挙動・打刻との並行実行を測るべきです。[Utilities.computeDigest](https://developers.google.com/apps-script/reference/utilities/utilities)

### 台帳と照合処理の設計が不足している

直近8日のファイル名だけを調べる週次検査では、以下を検出できません。

- `COMPLETED` 後にファイルが削除・移動・差替えされた
- 週次トリガーが8日以上止まった
- 同名ファイルの内容が異なる
- 台帳リンクだけが壊れた

低件数なので、全件または当年＋前年を `drive_file_id` で検査する方が単純で確実です。`last_successful_scan_at` を保存し、欠落・重複・ハッシュ不一致ごとの復旧手順も用意してください。

### 訂正・取消フローがない

誤金額、取引先、区分、事業割合を `COMPLETED` 後にどう直すかがありません。システム列を直接上書きすると監査証跡とハッシュの意味が失われます。

少なくとも、元の受付IDを参照する `CORRECTED`／`VOID` 行、訂正理由、訂正日時を追加するか、明文化した手動訂正手順と変更履歴を用意してください。

### スプレッドシート移行と保護が弱い

既存の経費ヘッダーは14列で、数値・日付書式や保護対象にも入っていません。[sheets.ts](/Users/takenouchiharuhi/projects/kadobo/gas/src/adapters/sheets.ts:86)

- 単なる「不足列を末尾追加」ではなく、既存ヘッダーの完全一致確認、バックアップ、バージョン付き移行にする。
- 受付ID、状態、Drive ID、ハッシュ、リンクなどのシステム列を保護・非表示にする。
- `メモ` にシステムエラーを混在させず、`last_error` と `state_updated_at` を分ける。
- 金額上限9,999,999円は要件にない追加制限なので、承認を得るか撤廃する。
- 文字列先頭の `=`, `+`, `-`, `@` による Sheets 数式注入を防ぐ。

### リリース／ロールバック順が不足している

プロトコル追加は Worker と GAS の同時整合を必要とします。

1. 電子取引フラグを既定OFF
2. Sheetsをバックアップし、GASの後方互換実装と移行を先にデプロイ
3. Workerをデプロイ
4. 疎通試験
5. 紙証憑のみ有効化
6. 法令ゲート完了後に電子取引を有効化

ロールバック時は、pending の `expense_submit` がなくなるまで旧GASへ戻さないか、新旧プロトコルを両方処理できる期間を設ける必要があります。

## 4. 改善提案

- `ENABLE_EXPENSE` と `ENABLE_E_DOC` を Worker・GAS双方で検査する。モーダルで選択肢を隠すだけでは、pending request や古いクライアントを止められない。
- `DRIVE_RECEIPT_ROOT_ID` は自動作成・自動書戻しより、手動作成して設定し、欠落時は fail closed とする方が安全。
- 完了DMの送信失敗を完全に握り潰さず、`notify_status` を残す。経費は登録済みなのに利用者が再入力する二重登録誘因になる。
- `url_private` をD1へ長期保存せず、file IDと必要なメタデータを保存する。
- SHA-256 は法的必須ではないが、今回の再照合と重複検知には有用なので残す。
- `partner` の空白正規化、ファイル拡張子の小文字化、Unicodeを壊さないファイル名切詰めを仕様化する。
- HEIC が Drive／ブラウザ／印刷で実際に閲覧できるか確認する。画像として受理できても、可視性を満たすとは限らない。
- 月次バックアップに経費台帳だけでなく証憑フォルダを含め、別障害ドメインへの保存を検討する。

作業パッケージについては、WP5を先に置く方向はよいものの、WP8が広すぎます。「台帳スキーマとポート」「sagaと故障注入」「照合と運用復旧」に分けるべきです。WP9も法令前提、デプロイ、受入試験を分離してください。数値見積もりがないため見積精度そのものは評価不能ですが、WP8、S2、S4は明らかに過小評価されやすい範囲です。

§8に追加すべきスパイク／リスクは、Slack保存バイト列の同一性、モバイル版 `file_input`、同名Driveファイル、保存副作用後の例外、Slack 429・権限取消、Drive容量不足、Worker CPU／`waitUntil`、GASロック競合、HEIC可視性、週次トリガー停止、スキーマ移行失敗です。

## 5. 法令面の確認結果

### 電子取引データの保存方針

タイムスタンプを使わず、「訂正削除防止に関する事務処理規程」を備え付けて運用する方式は、電子取引データの真実性確保手段として認められています。ただし、規程を置くだけでは足りず、実際の訂正・削除手順、責任者、対象データ、運用記録が必要です。[国税庁 電子取引関係一問一答](https://www.nta.go.jp/law/joho-zeikaishaku/sonota/jirei/pdf/03-7.pdf)、[国税庁 参考資料・規程サンプル](https://www.nta.go.jp/law/joho-zeikaishaku/sonota/jirei/0021006-031.htm)

可視性についても、Drive上のファイルとSheets台帳をリンクし、ディスプレイ表示・印刷・ダウンロード要求に応じられるなら成立し得ます。しかし、設計書には「どの操作で検索・一覧出力・原本ダウンロード・印刷を行うか」の手順が不足しています。法令ゲートG1には、規程だけでなくシステム概要書、操作説明書、検索・提示・一括出力手順を含めてください。[国税庁 チェックシート](https://www.nta.go.jp/law/joho-zeikaishaku/sonota/jirei/tokusetsu/pdf/0024011-003_02.pdf)

### 検索要件の緩和

基準期間の売上高が5,000万円以下で、税務職員によるダウンロードの求めに応じられる場合、検索機能の確保は不要となるという理解は概ね正しいです。新規開業者の開業初年・翌年は基準期間がないため、検索要件は不要とする国税庁の説明もあります。[電子取引関係一問一答](https://www.nta.go.jp/law/joho-zeikaishaku/sonota/jirei/pdf/03-7.pdf)

ただし、

- 毎年、基準期間と売上高を再判定する
- ダウンロードの求めに実際に応じられるエクスポート手段を維持する
- 検索免除でも、見読可能性や真実性確保は免除されない

という条件を設計・運用に追加すべきです。

### スクリーンショットの扱い

設計の「スクリーンショット不可」は誤りです。国税庁は、電子取引データについてPDF化やスクリーンショットでの保存が可能である旨を示しています。[国税庁 電子取引データ保存教材](https://www.nta.go.jp/taxes/sake/hambai/moderutekisuto/pdf/r06_07_01.pdf)

もちろん、ダウンロード可能な請求書原本があるのに取引情報が欠けた画面だけを保存する運用は避けるべきです。しかし、それは「スクリーンショットだから違法」なのではなく、必要な取引情報や可読性を欠く可能性があるためです。

### 紙で受領した領収書

紙原本を法定保存し、撮影画像を検索・業務処理上の補助として扱うことは可能です。スキャナ保存は、紙をスキャンしたデータを紙原本に代えて保存する制度です。したがって、紙を廃棄せず、画像を法定原本の代替として主張しない限り、撮影しただけでスキャナ保存制度へ強制的に移行するわけではありません。[国税庁 スキャナ保存関係一問一答](https://www.nta.go.jp/law/joho-zeikaishaku/sonota/jirei/pdf/0022006-083_05.pdf)

運用規程には「紙証憑は紙が原本」「画像は補助」「保存期間満了まで紙を廃棄しない」と明記してください。

なお、設計書の「スキャナ保存にはタイムスタンプや外部サービス契約が必須」という趣旨は正確ではありません。訂正・削除履歴等を確認でき、時刻を客観的に証明できるシステムを使う場合はタイムスタンプを省略できる場合があります。ただし、現在の単純なSheets＋Drive構成がその要件を満たすとは考えにくいため、今回はスキャナ保存を採用しないという結論自体は妥当です。

### 保存期間

個人事業者では、帳簿、決算関係書類、現金預金関係書類などで5年・7年の区分があり、青色／白色、書類種別、消費税の適格請求書等でも扱いが異なります。[国税庁 個人で事業を行っている方の記帳・帳簿等の保存](https://www.nta.go.jp/taxes/shiraberu/shinkoku/kojin_jigyo/index.htm)

本システムで一律7年間保存する方針は保守的で妥当です。ただし「登録日から7年」ではなく、税法上の起算日を運用規程に記載し、自動削除を行わない設計にしてください。

### 「受領後7営業日」の入力期限

選択している事務処理規程方式について、「受領後7営業日以内に台帳入力しなければならない」という法定期限は確認できません。7営業日という期間は、主としてタイムスタンプを「速やかに」付す期間等の文脈で現れるものです。[電子取引関係一問一答](https://www.nta.go.jp/law/joho-zeikaishaku/sonota/jirei/pdf/03-7.pdf)

したがって、設計書では「法定期限」ではなく、漏れ防止のための社内運用SLAとして明記してください。事務処理規程に7営業日と書くなら、自ら定めた規程を守れる督促・例外処理が必要です。

## 6. 過剰設計・削ってよい部分

- 月数件〜数十件なら、複雑な「直近8日差分」の週次検査より、当年または全件を `drive_file_id` で照合する方が簡単で堅牢です。
- 4列程度の変更に汎用的な自動スキーママイグレーターを作る必要はありません。バックアップ付きの一回限りのバージョン移行で十分です。
- Driveルートの自動作成・プロパティ自動書戻しは削ってよいです。手動設定＋欠落時停止の方が誤ったフォルダ乱立を防げます。
- #E1 の条件付きチェックボックスは、法的価値がなく誤解を生むため削除または全面再設計してよいです。
- D1とSheetsの二重冪等性、処理状態、決定的受付IDは過剰ではありません。外部副作用を伴う at-least-once 配送には必要です。
- SHA-256も法的必須ではありませんが、重複検知・ファイル差替え検出に利用するなら残す価値があります。

## 7. 設計書 §7 の逸脱 #E1〜#E6 への評価

| 項目 | 評価 | 理由 |
|---|---|---|
| #E1 電子取引＋画像の警告を条件付き必須チェックへ変更 | **却下** | スクリーンショット不可という法令解釈が誤っており、適法なWeb取引データを拒否します。値もプロトコル・台帳に残らず、証跡になっていません。原本優先の案内と、取引情報・可読性の確認へ置き換えるべきです。 |
| #E2 台帳行を先に確保する方式 | **要再考** | 受付行を先に確保する方向は正しいですが、現状は `RECEIVED`／`FILE_SAVED` の再開点がなく、Drive保存の重複を防げません。状態別再開と既存ファイル検索を追加した場合に限り妥当です。 |
| #E3 モーダル再表示時に前回選択を引き継がない | **妥当** | 件数が少なく、誤った前回値を黙って再利用するより、利用者が最終値を明示選択する方が安全です。入力負荷も許容範囲です。 |
| #E4 非同期失敗時に再実行ボタンを設けない | **妥当** | 一時障害は同一冪等キーで自動再試行し、恒久的な入力不備は新規入力にする方が、手動再実行とCronの競合を避けられます。ただし、再試行可能／恒久エラーの分類、停止回数、具体的な再入力案内、完了DM失敗時の扱いが必要です。 |
| #E5 事業割合等をモーダルから除外 | **要再考** | 「免税事業者なので使わない」は理由になりません。事業使用割合は所得税上の家事按分にも関係します。モーダルに残すか、少なくとも月次確定時に必ず設定・確認する運用が必要です。消費税区分を将来対応として空欄にする判断とは分けてください。 |
| #E6 冪等キー・Slack file ID等のシステム列追加 | **妥当** | at-least-once 配送と照合のため必要です。ただし、Slack file IDだけではDrive側の存在確認ができないため `drive_file_id`、元ファイル名、状態更新日時も追加し、システム列を保護してください。 |
